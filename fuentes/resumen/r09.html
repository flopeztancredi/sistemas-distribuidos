App Engine y BigTable

Google App Engine muestra cómo una PaaS fuerza aplicaciones replicables y administra versiones, instancias, colas y almacenamiento. BigTable muestra el soporte de datos: tabla dispersa, particionada por rangos y servida por tablet servers coordinados mediante metadata y Chubby.

PaaS en detalle

Una PaaS recibe código o un artefacto y administra runtime, aislamiento, despliegue, balanceo, escalado, health checks, logs y servicios asociados. Para poder crear y destruir instancias libremente, la aplicación debe:

  • no depender del disco local para estado durable;
  • responder pedidos dentro de límites;
  • usar servicios externos para datos, cache y colas;
  • tolerar múltiples instancias y reintentos;
  • declarar configuración y dependencias de modo reproducible.

La plataforma restringe para ganar capacidad de operación. El costo es menor control del host, límites de runtime y dependencia de APIs del proveedor.

Google App Engine

La jerarquía lógica es:

aplicacion
  servicio A
    version A1 -> instancias xN
    version A2 -> instancias xM
  servicio B
    version B1 -> instancias xK
  • Aplicación: unidad administrativa y de recursos.
  • Servicio: componente con configuración y escala propias.
  • Versión: artefacto desplegado e inmutable, útil para rollback y tráfico gradual.
  • Instancia: proceso concreto creado según demanda.

Un frontend recibe tráfico, resuelve aplicación, servicio y versión, y balancea entre instancias. El scheduler puede crear instancias por carga y retirarlas. Separar versión de instancia permite canary, blue green y rollback sin editar procesos vivos.

El entorno original restringía filesystem, sockets y duración para que cualquier request pudiera ejecutarse en cualquier instancia. Las tareas largas se enviaban a colas. Aunque los runtimes modernos sean más flexibles, la idea de diseño se conserva: estado durable fuera de la instancia.

Push, pull y leasing

En una push queue, la plataforma invoca un handler HTTP y reintenta si no obtiene éxito. El handler debe ser idempotente. Tasa, concurrencia y backoff protegen al servicio.

En una pull queue, workers piden tareas y reciben un lease. Durante el lease nadie más debería tomarlas. Si el worker termina, elimina la tarea. Si cae, el lease vence y otro la recibe. Un lease reduce ejecución simultánea, pero no evita duplicado si el worker produjo el efecto y cayó antes de borrar.

tarea disponible
    -> lease por T segundos
        -> exito: delete
        -> fallo o timeout: vuelve a disponible

Datastore y partición

Datastore ofrece entidades con key y propiedades sobre una infraestructura particionada. La clave determina identidad y ubicación. Los grupos de entidades permiten transacciones fuertes dentro de un alcance acotado, pero una raíz demasiado popular concentra escrituras.

La lección general es que el límite transaccional debe coincidir con el agregado del dominio. Una transacción global fácil de pedir es difícil de escalar. Índices permiten consultas, pero cada índice agrega escrituras y almacenamiento.

Modelo de BigTable

BigTable. Mapa ordenado, distribuido, persistente y disperso indexado por (row key, column key, timestamp).

Las filas se ordenan lexicográficamente por row key. Las columnas se agrupan en column families declaradas, mientras calificadores pueden aparecer dinámicamente. Cada celda conserva versiones por timestamp. “Disperso” significa que una celda inexistente no ocupa lugar.

(row_key, family:qualifier, timestamp) -> bytes

web.example/page42
  contenido:html  @t3 -> ...
  metricas:vistas @t5 -> 918
  links:a         @t2 -> destino

La row key domina localidad y carga. Campos que se consultan juntos conviene que queden en filas cercanas. Una clave monotónica concentra escrituras nuevas en el último rango. Se evita anteponiendo hash, bucket o identificador distribuido, aceptando que ciertas consultas por rango necesitarán fan out.

Tablets y jerarquía

Tablet. Rango contiguo de filas servido como unidad de partición y asignación.

La localización usa tres niveles conceptuales:

  1. Chubby conserva la ubicación del root tablet.
  2. El root tablet contiene ubicaciones de tablets de metadata.
  3. Las tablets de metadata indican qué tablet de usuario contiene una row key.

El cliente cachea ubicaciones. Si consulta el tablet equivocado, invalida y vuelve a resolver. La jerarquía evita un directorio central enorme en cada lookup.

Master, tablet servers y Chubby

  • Master: asigna tablets, detecta altas y bajas, balancea y coordina cambios de esquema. No está en el camino normal de cada lectura o escritura.
  • Tablet server: sirve tablets, mantiene memoria, logs y archivos persistentes, y divide tablets grandes.
  • Chubby: servicio de locks y archivos pequeños con consistencia fuerte, usado para elección de master, membresía y bootstrap.

Separar control y datos evita que el master sea cuello de botella de I/O. Si cae, los tablet servers pueden seguir sirviendo durante un período mientras se elige otro, aunque cambios de asignación se pausen.

Camino de escritura y lectura

Una escritura llega al tablet server, se agrega a un commit log durable y a una estructura en memoria. Cuando crece, se vuelca a archivos ordenados inmutables. Compactions combinan archivos y descartan versiones vencidas. Una lectura consulta memoria y archivos relevantes, ayudada por índices y filtros.

Cuando una tablet supera un umbral, se divide por rango. El master reasigna partes. El balance depende de que las row keys no concentren tráfico en una única tablet, aunque haya muchas máquinas libres.

En BigTable casi toda pregunta vuelve a la row key. Hay que poder dibujar la jerarquía Chubby, root, metadata, tablet y explicar por qué una clave monotónica crea hotspot.
