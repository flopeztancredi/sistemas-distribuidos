Protocolos e invocación remota

Esta sección concentra las decisiones que permiten que dos componentes se entiendan: separación lógica y física, contratos, protocolo de mensajes y abstracciones de invocación. Cliente servidor, REST, RPC y objetos distribuidos se comparan acá como alternativas completas, sin anticipos en otros capítulos.

Layers y tiers

Layer. División lógica de responsabilidades. Cada capa ofrece servicios a la superior y usa servicios de la inferior.
Tier. Unidad física de despliegue. Indica en qué proceso o máquina corre una parte.

Presentación, negocio y persistencia pueden ser tres layers dentro de un único ejecutable, o desplegarse en tres tiers. Cambiar layers mejora modularidad. Cambiar tiers modifica latencia, seguridad, escalabilidad y fallos.

Un modelo lógico frecuente separa Presentation y API como entradas, Services como coordinación de casos de uso, Core Business como reglas y entidades, y Persistence como acceso a datos. Security y Audit son responsabilidades transversales. En un despliegue 3 tier, el cliente corre presentación, un servidor ejecuta negocio y otro aloja la base. Los layers no deben confundirse con esas máquinas.

Una dependencia normal baja desde una capa de mayor nivel hacia una abstracción de menor nivel. Un upcall permite que una capa inferior notifique a una superior mediante callback, evento o interfaz invertida. Si dos layers se conocen mutuamente por sus implementaciones aparece dependencia circular, que dificulta probar y reemplazar.

“Arquitectura de tres capas” no dice cuántas máquinas hay. “Arquitectura de tres tiers” sí afirma una separación de despliegue, pero no prueba que cada tier tenga una sola responsabilidad lógica.

Interfaces y contratos

Interfaz. Frontera pública que permite comunicar componentes, servicios o sistemas mediante un contrato, ocultando la implementación privada.

Una interfaz lista operaciones accesibles. Un contrato además fija precondiciones, postcondiciones, invariantes, tipos, errores y semántica observable. En una interfaz remota también debe definir:

  • identidad y versionado de recursos;
  • autenticación, autorización y límites de uso;
  • timeouts esperados y cancelación;
  • idempotencia y deduplicación;
  • orden, consistencia y visibilidad de escrituras;
  • compatibilidad hacia atrás de consumidores y productores.

Un contrato orientado a entidades expone recursos y cambios de estado. Uno orientado a procesos expone acciones o procedimientos. Ninguno es universalmente mejor: entidades favorecen una interfaz uniforme y procesos modelan operaciones de negocio complejas sin fingir que todo es CRUD.

Orientados a entidades: GET /users/{id} y POST /products. Orientados a procesos: POST /search y POST /transform/html-to-pdf. El primero identifica sustantivos y usa la operación estándar; el segundo nombra una acción cuyo resultado no se modela naturalmente como CRUD.

Las interfaces también se clasifican por alcance: Web API con HTTP, API remota custom sobre TCP o UDP, API orientada a procedimientos como gRPC, API orientada a objetos como CORBA o RMI, biblioteca o framework dentro del proceso, y API de sistema operativo como POSIX o WinAPI.

Qué define un protocolo

Protocolo. Acuerdo sobre formato, significado, orden y temporización de mensajes entre participantes.

La sintaxis indica campos y codificación. La semántica indica qué significa cada valor y qué efecto produce. La secuencia indica qué mensajes son válidos en cada estado. La temporización define timeouts, retransmisiones y vigencia.

Cada capa intercambia una PDU compuesta por control propio y payload de la capa superior. Al enviar, las capas encapsulan. Al recibir, desencapsulan y validan.

PDU. Unidad de datos que un protocolo entrega a la capa inferior para ser encapsulada.

Si una PDU supera el máximo inferior, se segmenta y cada fragmento repite headers. Si varias PDUs pequeñas caben juntas, batching amortiza headers a costa de esperar y sumar latencia. El protocolo de aplicación debe conocer qué garantiza la capa inferior: una imagen grande sobre UDP puede perderse completa por faltar un solo fragmento.

Dos protocolos para el mismo registro

Para {email: string, nacimiento: date}, una alternativa textual es una línea JSON en UTF-8 terminada por salto:

{"email":"ana@example.com","nacimiento":"2001-04-23"}\n

Es legible y extensible, pero el delimitador debe respetar strings escapados y el parseo cuesta más. Una alternativa binaria usa header fijo y campos con longitud:

version:u8 | email_len:u16 | email:bytes | dias_desde_epoch:i32

Es compacta y determinista, pero necesita acordar endianness, encoding, rango de fecha y evolución. Ejemplos no binarios conocidos son HTTP en su forma textual, JSON y SMTP. Protocolos o formatos binarios incluyen Protocol Buffers, MessagePack y las capas binarias modernas de HTTP/2.

Cliente servidor y peer to peer

Cliente servidor. El cliente inicia pedidos y el servidor escucha, procesa y responde. El rol describe una interacción, no necesariamente una máquina permanente.

Ventajas: autoridad y estado fáciles de ubicar, clientes simples, seguridad y operación centralizadas. Límites: capacidad concentrada, dependencia del servidor y necesidad de escalar o replicar ese rol.

Un servidor no inicia espontáneamente una conexión cliente servidor, pero puede entregar novedades de varias formas:

  • Polling: el cliente pregunta periódicamente. Simple, con demora o tráfico inútil.
  • Long polling: el servidor retiene el pedido hasta tener novedad o vencer.
  • Streaming: una conexión iniciada por el cliente permanece abierta y transporta eventos.
  • Callback: el cliente ofrece otro endpoint y pasa a ser servidor para esa devolución.
Peer to peer. Participantes con roles equivalentes se descubren y se comunican directamente según un protocolo común.

P2P distribuye recursos y evita una autoridad de datos única, pero complica membresía, búsqueda, NAT, firewalls, confianza y consistencia. Un diseño híbrido suele usar registro central para discovery y conexiones directas para datos.

HTTP y REST

HTTP es un protocolo request response. Método, URL, headers y body forman el pedido; status, headers y body forman la respuesta. Es stateless a nivel de protocolo: cada pedido debe incluir el contexto necesario, aunque la aplicación pueda mantener sesión externa.

Una arquitectura REST respeta:

  • Cliente servidor: separación de interfaz y almacenamiento.
  • Stateless: cada request se interpreta por sí mismo.
  • Cache: las respuestas declaran si pueden reutilizarse.
  • Interfaz uniforme: recursos identificados por URI, representaciones, mensajes autodescriptivos e hipermedia cuando corresponde.
  • Sistema por capas: el cliente no necesita saber si habla con origen, proxy o cache.
  • Code on demand opcional: el servidor puede enviar código ejecutable.

La parte de hipermedia se conoce como HATEOAS: una representación incluye links a acciones o estados siguientes para que el cliente los descubra. Es parte de la definición académica de REST, aunque muchas APIs HTTP de producción no la implementan de forma completa.

Códigos típicos: 200 lectura exitosa, 201 creación, 202 aceptado para procesar luego, 204 éxito sin body, 400 pedido inválido, 401 falta autenticación, 403 identidad sin permiso, 404 inexistente, 409 conflicto de estado, 429 límite, 500 fallo interno y 503 indisponibilidad transitoria.

Las URLs identifican entidades, no pantallas ni verbos arbitrarios: /orders/42. Relaciones se expresan con subrecursos o enlaces. El versionado puede estar en path, header o media type; la regla importante es hacer cambios aditivos y tolerar campos desconocidos antes de romper consumidores.

Semantic Versioning. Versión Major.Minor.Patch: Major cambia ante incompatibilidad de contrato, Minor agrega funcionalidad compatible y Patch corrige sin cambiar la interfaz.

Versionar la API no es versionar una entidad. La primera decisión permite que consumidores viejos convivan durante una migración. El versionado histórico conserva estados sucesivos del mismo recurso, por ejemplo revisiones de una página. Una API puede exponer /v2 y, dentro de ella, muchas revisiones de cada entidad.

RPC y gRPC

RPC. Abstracción que permite invocar un procedimiento remoto mediante una interfaz parecida a una llamada local.

Una IDL define operaciones y tipos sin depender del lenguaje. Un generador produce client stub y server stub. El stub cliente serializa argumentos, envía y espera. El servidor deserializa, invoca la implementación y serializa resultado o error. Marshalling incluye representación portable de tipos, endianness, strings y referencias.

aplicacion cliente
    -> client stub
        -> marshalling -> transporte -> unmarshalling
            -> server stub -> procedimiento
    <- resultado o error por el camino inverso

Fallos y call semantics

Si vence un timeout, el cliente no sabe si el servidor no recibió, ejecutó y perdió la respuesta, o sigue trabajando. Las semánticas posibles son:

  • Maybe: se intenta una vez, puede no ejecutarse.
  • At least once: se reintenta hasta observar respuesta, puede ejecutar varias veces.
  • At most once: se usan identificadores y cache de resultados para suprimir duplicados, puede no ejecutar si no se recupera.
  • Exactly once: requiere que efecto y registro de deduplicación sean atómicos y recuperables. No surge solo por usar RPC.

Las operaciones idempotentes toleran repeticiones respecto de su estado final. Para las demás, el cliente envía una idempotency key estable y el servidor persiste clave, estado y resultado.

Para trabajos de minutos no se deja una llamada bloqueada indefinidamente:

POST trabajo(idempotency_key) -> 202 {job_id}
GET  trabajo/{job_id}        -> pendiente | ejecutando | listo | error
GET  trabajo/{job_id}/resultado

gRPC usa contratos Protocol Buffers, generación de stubs y HTTP/2. Soporta llamada unaria, stream del servidor, stream del cliente y stream bidireccional. Deadlines y cancelación deben propagarse. Su interfaz orientada a procedimientos es útil entre servicios controlados, mientras REST suele ser más accesible para APIs web públicas.

Objetos distribuidos, CORBA y RMI

Un objeto distribuido expone identidad, estado y métodos remotos. Un middleware conserva referencias y enruta invocaciones. RPC llama procedimientos de un servicio; el modelo de objetos intenta extender semántica orientada a objetos a través de la red.

CORBA define IDL independiente del lenguaje, ORB para localizar objetos y transportar invocaciones, stubs, skeletons y servicios auxiliares. Java RMI aplica una idea similar dentro del ecosistema Java: interfaz remota, registry, stubs y serialización de objetos.

Su uso disminuyó porque referencias remotas, garbage collection distribuido, compatibilidad de tipos y llamadas pequeñas encadenadas vuelven frágil la abstracción. Hoy se prefieren servicios más gruesos y contratos explícitos.

Operaciones sobre varios objetos

Que dos cuentas sean objetos remotos no vuelve atómica una transferencia:

origen = registry.lookup("CA-1234")
destino = registry.lookup("CA-5678")

tx = coordinador.begin()
origen.extraer(tx, 1000)
destino.acreditar(tx, 1000)
coordinador.commit(tx)        # requiere protocolo como 2PC

Sin coordinador transaccional, una caída entre ambas llamadas deja un efecto parcial. También se puede modelar una transferencia como recurso con estado e idempotency key y completar por saga. La frontera de objeto no reemplaza el protocolo de commit.

CLIENTE
  AccountProxy("CA-1234") ----\
                               \ RPC
  AccountProxy("CA-5678") ------> DISPATCHER DEL SERVIDOR
                                      |
                                      +-> Account CA-1234
                                      |     saldo: 1000 -> 800
                                      |
                                      \-> Account CA-5678
                                            saldo: 500 -> 700

El proxy conserva referencia remota, no una copia del saldo.
El dispatcher usa identidad de objeto para dirigir cada invocacion.
Para comparar REST y RPC, no alcanza con JSON contra binario. Compará orientación del contrato, descubribilidad, generación de clientes, streaming, cache, compatibilidad y tratamiento de fallos remotos.
