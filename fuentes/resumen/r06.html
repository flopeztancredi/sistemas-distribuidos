Cómputo distribuido

Distribuir cómputo exige asignar trabajo, mover datos, detectar terminación y recuperarse. MapReduce, MPI, Flink y Beam eligen puntos distintos del espacio: batch tolerante a fallos, coordinación explícita de alto rendimiento, streaming con estado y modelo portable.

Coordinar actividades

Un coordinador debe responder:

  • qué tareas existen y cuáles están listas;
  • qué worker tiene cada tarea y qué lease limita esa asignación;
  • dónde viven input, estado intermedio y output;
  • cómo detectar caída sin confundirla con lentitud;
  • cuándo reintentar y cómo evitar doble efecto;
  • cómo saber que el trabajo global terminó.

La arquitectura master worker funciona bien cuando las tareas son independientes y el master maneja metadata, no todo el flujo de datos. Para evitar cuello de botella, los workers leen y escriben directamente en almacenamiento distribuido.

MapReduce

MapReduce. Modelo batch que transforma pares clave valor con una fase paralela map, agrupa por clave y aplica una fase reduce por grupo.
map(k1, v1)       -> lista de (k2, v2)
shuffle y sort    -> k2, [v2, v2, ...]
reduce(k2, vals)  -> lista de resultados
Contar palabras: map emite (palabra, 1) por aparición. Shuffle agrupa todos los unos de una palabra. reduce los suma.

Una ejecución típica:

  1. Particionar archivos de entrada en splits.
  2. Asignar cada split a un mapper, preferentemente cerca de sus datos.
  3. El mapper emite pares intermedios, los divide por reducer con una función de partición y materializa archivos intermedios locales para el shuffle.
  4. Un combiner opcional agrega localmente si la operación es asociativa y conmutativa.
  5. Shuffle transfiere cada partición al reducer correspondiente y sort agrupa claves.
  6. Cada reducer procesa una clave y escribe output durable.

Si un mapper cae se reejecuta porque su input es durable y su salida intermedia es regenerable. Si un reducer cae, se repite desde los intermedios. Tareas lentas pueden ejecutarse especulativamente en otro worker y aceptar el primer resultado. Esto exige funciones deterministas o efectos controlados.

MapReduce no es cualquier master worker. Su forma clave valor, shuffle y reejecución determinista son lo que permiten paralelizar y recuperar automáticamente.

Diseñar varias salidas

Para logs (email, url, fecha) se pueden ejecutar jobs o ramas:

navegaciones por dia:
    map:    emit(dia_semana(fecha), 1)
    reduce: emit(dia, sum(valores))

URL mas vista:
    map:    emit(url, 1)
    reduce: emit(url, sum(valores))
    job final: max por cantidad

emails con mas de 10:
    map:    emit(email, 1)
    reduce: total = sum(valores); emitir si total > 10

Calcular “más que la media global” suele requerir dos pasos: primero suma y cantidad global, luego filtrar entidades con ese umbral. Una condición de días consecutivos requiere que el reducer reciba todas las fechas de una cuenta, las ordene o las represente como conjunto y detecte adyacencia.

DAG para métricas de ventas

leer ventas
  +-> expandir items -> sumar cantidad por producto -> top 10
  +-> total por venta -> min, max, suma, count -> promedio
  \-> contar items por venta -> filtrar mayor que 3 -> count

las tres ramas se unen solo para publicar el reporte

El grafo muestra paralelismo y dependencias. Cada agregación parcial debe ser asociativa para combinarse jerárquicamente sin un único reducer prematuro.

MPI y Open MPI

MPI. Estándar de pasaje de mensajes para programas paralelos donde procesos conocidos coordinan explícitamente comunicación punto a punto y colectiva.

Todos los procesos ejecutan el mismo programa en el modelo SPMD, pero usan su rank dentro de un communicator para tomar roles diferentes. El tamaño del communicator indica cuántos participan.

Las operaciones colectivas se invocan en el mismo orden desde todos los ranks del communicator. En Bcast, por ejemplo, el root aporta el buffer y los demás participan en la misma llamada para recibirlo. Saltear la colectiva en un rank puede bloquear al resto.

estimar pi por Montecarlo:
    rank, n = MPI.rank(), MPI.size()
    muestras_locales = dividir(total, n, rank)
    aciertos = contar_puntos_dentro_del_circulo(muestras_locales)
    aciertos_totales = MPI.Reduce(aciertos, SUM, root=0)
    if rank == 0:
        pi = 4 * aciertos_totales / total

MPI apunta a performance y control, no a elasticidad o recuperación automática de procesos. Un Send bloqueante puede esperar buffer o recepción según implementación y tamaño. Dos procesos que hacen envíos bloqueantes cruzados antes de recibir pueden quedar trabados. Se evita ordenando operaciones o usando variantes no bloqueantes y luego Wait.

Apache Flink

Flink ejecuta dataflows con operadores y streams. Un batch es un stream acotado. Los operadores pueden mantener estado particionado por clave y procesar eventos continuamente.

Tiempo y ventanas

  • Processing time: reloj de la máquina que procesa. Baja latencia, resultado dependiente de demoras.
  • Event time: timestamp del evento. Permite reconstruir la semántica del origen aunque llegue tarde.
  • Ingestion time: timestamp al entrar al sistema, compromiso menos expresivo.

Una tumbling window divide intervalos sin solapamiento. Una sliding window solapa intervalos según tamaño y paso. Una session window agrupa actividad separada por gaps. Una ventana global requiere un trigger adicional.

Watermark. Estimación de que no llegarán eventos con event time menor que cierto valor. Permite cerrar ventanas tolerando un atraso configurado.

Los eventos más tardíos que el margen pueden descartarse, actualizar resultados o ir a una salida lateral. No existe un watermark perfecto sin esperar para siempre.

Arquitectura y recuperación

El JobManager coordina jobs, scheduling y checkpoints. TaskManagers ofrecen slots y ejecutan subtareas. Los operadores se encadenan cuando conviene para evitar serialización y red. keyBy particiona estado y eventos de una misma clave hacia la misma instancia lógica.

Los checkpoints insertan barreras en los streams. Cuando un operador recibió la barrera de todos sus inputs, captura un estado consistente y propaga. Ante caída, se restaura el último checkpoint y se reproducen fuentes capaces de replay. Exactly once respecto de un sink externo requiere un conector transaccional o idempotente, no solo checkpoint interno.

Apache Beam

Beam separa un modelo de programación de sus motores de ejecución. El programa construye un pipeline de PCollections y PTransforms. Un runner lo ejecuta sobre Flink, Spark, Dataflow u otro backend compatible.

Su modelo responde cuatro preguntas para agregaciones no acotadas:

  • Qué: qué valores se agregan.
  • Dónde en event time: qué ventana los agrupa.
  • Cuándo: qué trigger emite resultados.
  • Cómo: si cada emisión descarta o acumula resultados anteriores.
