Datos distribuidos

Distribuir datos combina tres decisiones distintas: modelo de almacenamiento, replicación y partición. Replicar mejora lecturas y tolerancia a fallos, particionar reparte capacidad, y cada combinación define consistencia, ruteo y recuperación.

Una base relacional ofrece esquema, relaciones, constraints y lenguaje de consulta general. NoSQL agrupa modelos clave valor, documentos, columnas anchas y grafos. La elección depende de accesos, invariantes y escala, no de una oposición entre “SQL lento” y “NoSQL rápido”.

  • Almacenamiento por filas: mantiene juntos los campos de una entidad. Conviene leer o escribir filas completas.
  • Columnar: mantiene juntos valores de una columna. Comprime bien y lee solo columnas necesarias para analítica.
  • Cubo o vista materializada: precalcula agregaciones por dimensiones. Acelera consultas conocidas a costa de almacenamiento y actualización.

En gran escala, los datos atraviesan ingesta, almacenamiento crudo, validación, transformación, serving y archivo. Cada frontera debe definir formato, ownership, reintento, replay y control de calidad.

Replicación

Replicación. Mantener copias del mismo conjunto lógico para aumentar disponibilidad, cercanía o capacidad de lectura.

Leader based

Todas las escrituras pasan por un leader, que registra un orden y envía cambios a followers. Las lecturas pueden ir al leader para máxima actualidad o a followers aceptando lag. La replicación sincrónica espera una o más copias antes de confirmar; reduce pérdida ante fallo pero aumenta latencia y puede bloquear. La asincrónica confirma antes y admite perder cambios recientes si el leader cae.

El failover requiere detectar caída, elegir nuevo leader y redirigir. Un timeout demasiado corto produce elecciones innecesarias. Si dos lados aceptan escrituras como leader aparece split brain.

Multi leader

Varios leaders aceptan escrituras, útil entre regiones o clientes desconectados. Los cambios concurrentes pueden entrar en conflicto. Resolver por último timestamp puede perder datos y depende de relojes. Alternativas: merge específico del dominio, CRDT, conservar hermanos o asignar cada entidad a una región principal.

Leaderless y quorums

El cliente escribe a varias réplicas y lee varias. Con N copias, W confirmaciones de escritura y R respuestas de lectura:

si W + R > N, lectura y escritura intersectan al menos una replica
si W > N/2, dos escrituras de quorum intersectan

La intersección no garantiza por sí sola linearizabilidad: hay escrituras concurrentes, versiones, fallos y sloppy quorums. El lector elige la versión mediante números, vectores o reglas de conflicto y puede hacer read repair. Anti entropy compara réplicas en segundo plano.

Modelos de consistencia

  • Linearizable: cada operación parece ocurrir en un punto entre invocación y respuesta y respeta tiempo real.
  • Secuencial: existe un orden total consistente con el orden de cada proceso, no necesariamente con tiempo real.
  • Causal: todos respetan relaciones causales, operaciones concurrentes pueden verse en distinto orden.
  • Eventual: si cesan escrituras, las réplicas convergen, sin limitar cuánto tardan ni qué se lee antes.
  • Read your writes: un cliente no pierde de vista sus propias escrituras.
  • Monotonic reads: una vez vista una versión, el cliente no vuelve a una anterior.

La consistencia se especifica por operación y requisito. Un catálogo puede tolerar lectura atrasada; confirmar un pago o adquirir un lock suele requerir coordinación fuerte.

La clave debe acompañar el patrón de acceso y tener cardinalidad suficiente. Un tenant gigante puede romper una partición por tenant. Salting agrega un sufijo para repartir una clave caliente, pero obliga a consultar y combinar varios buckets.

El ruteo puede residir en el cliente, un proxy o cualquier nodo que reenvía. Resharding mueve rangos y actualiza metadata sin servir dos dueños inconsistentes. Las operaciones entre particiones agregan coordinación o se rediseñan como sagas y agregados independientes.

Distributed Shared Memory

DSM. Abstracción que presenta un espacio de memoria compartido sobre máquinas con memoria físicamente separada.
VarianteOperaciónConsistencia y costo
NaiveTodas las páginas viven en un servidor. Cada read o write es un request y el servidor serializa con locks.Consistencia simple, red en cada acceso, cuello y fallo único.
MigraciónEl servidor presta una página completa a un cliente. Si otro la pide, espera o la página migra desde el dueño actual.Una sola copia escribible evita conflictos, pero una página disputada hace ping pong.
Réplicas de solo lecturaLos reads crean mirrors locales. Los writes van al servidor, que invalida todos los mirrors.Lecturas locales rápidas, escrituras caras y tormenta de recarga si cambian seguido.
Réplicas de lectura y escrituraLos clientes escriben copias y un secuenciador central ordena y difunde cada actualización.Más concurrencia, pero coherencia, orden y recuperación son complejos.
 
replicacion de solo lectura:
    cliente sin pagina -> READ_PAGE al servidor
    servidor registra al cliente y devuelve mirror
    cliente lee localmente

    WRITE siempre llega al servidor
    servidor actualiza version
    servidor -> INVALIDATE(version) a cada mirror
    cada cliente descarta y vuelve a pedir cuando necesite

Esta variante conviene cuando hay muchas lecturas y pocas escrituras, por ejemplo tablas de configuración grandes que cambian raramente. Es perjudicial con escrituras frecuentes o false sharing, porque cada cambio invalida páginas completas y obliga a transferirlas de nuevo.

DSM simplifica algunos algoritmos, pero oculta una diferencia de costo enorme entre acceso local y remoto. La granularidad de página puede transferir datos sin relación y convertir dos variables independientes en contención. También desalienta diseñar particiones y ownership explícitos, por eso no suele ser la primera elección en multicomputing.

Distributed File Systems

Un DFS presenta archivos remotos con nombres, permisos y operaciones conocidas. Las preguntas centrales son ubicación de metadata, cache, consistencia, replicación, tamaño de bloque y conducta ante desconexión.

NFS

NFS permite montar un filesystem remoto. Una VFS del cliente traduce operaciones a RPC contra el servidor. Los file handles identifican objetos sin depender de una sesión permanente. El cache del cliente reduce red, pero obliga a definir cuándo revalidar atributos y datos. El diseño históricamente stateless simplifica reinicio del servidor, aunque locks y versiones modernas agregan estado.

aplicacion cliente
    -> VFS del kernel
        +-> filesystem local
        \-> NFS client -> RPC -> NFS server -> VFS -> disco

RPC Bind informa el puerto del servicio.
La misma interfaz POSIX decide si la operacion es local o remota.

Conviene para compartir directorios y archivos con semántica familiar en una LAN. Es perjudicial para procesamiento masivo con muchas operaciones pequeñas o para un dataset que excede y satura un servidor central.

HDFS

HDFS optimiza archivos grandes y acceso secuencial. El NameNode mantiene namespace y mapa de bloques. DataNodes guardan bloques grandes replicados. El cliente consulta metadata y transfiere datos directamente con DataNodes. Para escribir, el bloque atraviesa un pipeline de réplicas y se confirma según la política.

lectura:
    cliente -> NameNode: ubicaciones del bloque
    cliente -> DataNode cercano: bytes

escritura con factor 3:
    cliente -> DN1 -> DN2 -> DN3
    ACK vuelve DN3 -> DN2 -> DN1 -> cliente

Los DataNodes envían heartbeats y reportes de bloques. Si uno cae, el NameNode ordena re replicar hasta recuperar el factor. Rack awareness ubica copias en dominios distintos. Los bloques grandes reducen metadata y favorecen throughput; el costo es desperdicio o metadata excesiva con archivos pequeños.

HDFS mueve cómputo hacia datos y tolera hardware commodity. No está pensado para baja latencia, millones de archivos diminutos ni escrituras aleatorias generales. Su consistencia y patrón write once o append son deliberadamente más restringidos que POSIX.

Si piden elegir una arquitectura de datos, especificá clave de partición, réplicas, ruteo, consistencia y recuperación. Nombrar “NoSQL” no responde ninguna de esas decisiones.
