Diseño de gran escala

Diseñar para un final no consiste en nombrar componentes conocidos. NALSD obliga a fijar números, límites, flujos y fallos para que cada caja del diagrama tenga una razón cuantitativa. Los casos prácticos de la materia se reducen a un método repetible.

Método NALSD

NALSD. Non Abstract Large System Design, diseño de gran escala basado en requisitos concretos, estimaciones y arquitectura física verificable.
  1. Scope: listar casos de uso incluidos y excluidos.
  2. SLO: latencia, disponibilidad, frescura, durabilidad y recuperación.
  3. Entidades y API: datos, identidad, relaciones y operaciones.
  4. Volumen: requests por segundo, bytes, retención, picos y crecimiento.
  5. Flujos: camino de escritura, lectura, procesamiento y errores.
  6. Arquitectura: componentes, partición, replicación, colas, caches y geografía.
  7. Fallos: recorrer duplicados, caída, retry, backlog, pérdida de zona y recuperación.
  8. Tradeoffs: declarar qué se prioriza y qué se acepta degradar.

Las estimaciones usan órdenes de magnitud. No buscan adivinar hardware exacto, sino revelar qué domina:

QPS_promedio = operaciones_por_dia / 86400
QPS_pico     = QPS_promedio * factor_pico
ingesta_dia  = eventos_dia * bytes_evento
storage      = ingesta_dia * retencion_dias * replicas * overhead
ancho_banda  = eventos_segundo * bytes_evento
workers      = QPS_pico * tiempo_servicio_segundos / utilizacion_objetivo
Si llegan 40.000 imágenes diarias de 650 KB, la ingesta ronda 26 GB por día, 9,5 TB por año antes de réplicas. El promedio es menor a 1 imagen por segundo, pero una salida laboral puede concentrar miles en minutos. Dimensionar solo por promedio es incorrecto.

API y datos antes de las cajas

Los endpoints demuestran que el alcance es operable. Para videos de aulas:

POST /classrooms
POST /classrooms/{id}/videos       -> metadata + upload_url
GET  /classrooms/{id}
GET  /videos/{id}/playback-url
POST /videos/{id}/comments
GET  /videos/{id}/comments?cursor=...
GET  /rankings/videos?window=...

El binario grande usa object storage mediante URL prefirmada, no atraviesa la API. Metadata y comentarios usan base adecuada a sus consultas. Reproducciones se registran como eventos y el ranking se agrega por ventana, porque actualizar un contador global en cada play crea contención.

Vistas que debe tener la solución

  • Contexto: usuarios, sistema y externos.
  • Secuencia: flujo principal y respuesta asincrónica.
  • DAG: dependencias de procesamiento.
  • Física: regiones, zonas, instancias, stores, colas y enlaces.
  • Datos: entidades, claves de partición, índices y retención.

Un diagrama físico útil anota multiplicidad, protocolo, dirección, estado y dominio de fallo. Una caja “cloud” que contiene todo no permite evaluar escalabilidad.

Caso Web Crawler

Requisitos: partir de URLs, descargar hasta una profundidad, extraer links, evitar repetir, almacenar resultados y monitorear.

[Seeds]
   -> [Frontier particionada] -> [Fetchers xN] -> [Parsers xN]
            ^                                      |
            | links nuevos, depth + 1              v
       [Deduplicacion] <- hash(URL canonica)   [Object store]

[Eventos de estado] -> [Metricas y monitoreo]

La URL se canoniza antes de deduplicar. La frontier es una cola durable particionada por host para aplicar politeness y no sobrecargar un dominio. El fetch usa timeout, límite de tamaño y retry acotado. El parser emite links con profundidad. Al alcanzar el límite, guarda pero no realimenta.

Terminar no equivale a observar cola vacía: puede haber mensajes en vuelo que producirán nuevos links. El coordinador cuenta trabajo pendiente más leases activos, o usa una barrera de épocas. Contenido y metadata van a storage durable; monitoreo viaja por un flujo separado para no frenar el crawler.

Caso Shopping Cart

Requisitos típicos: carrito, stock, pago, pedido, notificaciones y seguimiento. La invariantes crítica es no vender más unidades de las disponibles y no cobrar dos veces.

Cliente -> API -> Order Service -> base de pedidos
                       |
                       +-> comando reservar -> Inventory
                       +-> comando cobrar   -> Payments
                       +-> evento           -> Notifications

estado: CREADO -> RESERVADO -> PAGADO -> CONFIRMADO
            \-> RECHAZADO     \-> COMPENSANDO

La API acepta con una idempotency key y devuelve order_id. Reservar stock es atómico dentro de la partición del producto, por ejemplo UPDATE ... SET stock = stock - q WHERE stock >= q. El pago usa otra clave idempotente.

No hay una transacción ACID única entre inventario, pago y notificación. Una saga persiste estado y ejecuta pasos con compensaciones: si el cobro falla, libera reserva; si se cobró pero la confirmación se demora, retry consulta por la misma clave. Un outbox escrito en la misma transacción que el pedido evita guardar estado sin publicar su evento.

Caso Traffic Violation Detector

Muchas cámaras producen imágenes, pero pocas contienen eventos relevantes. Filtrar en el borde reduce ancho de banda y almacenamiento central.

[Camaras] -> [Hub zonal: filtro y buffer]
                    |
          solo candidatos + metadata
                    v
             [Ingesta regional]
               |           |
          [Object store] [Cola]
                            v
                    [Reconocimiento xN]
                            v
                 [Casos y auditoria]

El hub tolera desconexión con buffer local y sube luego. Cada captura tiene ID global para deduplicar. La imagen grande va a object storage; la cola transporta referencia y metadata. El reconocimiento escala por backlog. Casos dudosos pasan a revisión humana y se conserva trazabilidad del modelo y evidencia.

La geografía importa: cámaras se agrupan en hubs cercanos, regiones reciben sus hubs y una capa global agrega metadata necesaria. Enviar todo crudo a un centro aumenta costo y crea una dependencia WAN.

Caso Shared Code Snippets

Separar metadata de contenido permite consultas y almacenamiento adecuados. Una clave aleatoria evita hotspot y dificulta enumeración. Si el contenido es inmutable, CDN y cache funcionan bien. Editar puede crear nueva versión y conservar historial.

POST /snippets {contenido, lenguaje, expiracion}
  -> {id, url}
GET /snippets/{id}
DELETE /snippets/{id}

[CDN] -> [API xN] -> [Metadata DB]
                    \-> [Object o blob store]
                         |
                    lifecycle por expiracion

La expiración no debe depender de un único cron que recorra toda la tabla. Se usa TTL nativo, índice por bucket temporal o lifecycle del store. El borrado lógico puede ocultar al instante y el físico ocurrir después.

Checklist de defensa

  • ¿Cuál es la clave de partición y puede calentarse?
  • ¿Qué componente conserva cada estado?
  • ¿Qué se confirma antes de responder éxito?
  • ¿Qué mensaje puede duplicarse y cómo se deduplica?
  • ¿Qué pasa si cada caja cae?
  • ¿Cómo se limita backlog y sobrecarga?
  • ¿Cómo se despliega una versión nueva y se revierte?
  • ¿Qué métricas prueban el SLO?
En finales de diseño se evalúa la cadena de razonamiento. Una respuesta sólida puede usar tecnologías distintas si demuestra volumen, flujo, estado, fallos y tradeoffs de forma coherente.
