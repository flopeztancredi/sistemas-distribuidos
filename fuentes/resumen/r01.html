Modelo distribuido y decisiones de diseño

Un sistema distribuido coordina computadoras autónomas mediante mensajes para ofrecer un resultado común. El punto de partida no es memorizar arquitecturas, sino entender qué cambia cuando no hay memoria, reloj ni destino de fallo compartidos, y qué decisiones compensan esas limitaciones.

Qué hace distribuido a un sistema

Sistema distribuido. Conjunto de computadoras independientes conectadas por una red que coordinan acciones intercambiando mensajes y que, para quien lo usa, se comportan como un sistema coherente.

La definición combina dos perspectivas que deben cumplirse a la vez:

  • Perspectiva interna: hay procesos autónomos, cada uno con memoria y control propios. La única evidencia directa sobre otro nodo llega por mensajes.
  • Perspectiva externa: la distribución no obliga al usuario a conocer dónde vive cada recurso ni qué nodo resolvió cada operación.

De la autonomía aparecen los problemas centrales de la materia:

  • No hay memoria global: dos nodos pueden observar versiones diferentes de un dato.
  • No hay reloj global perfecto: los timestamps físicos no bastan para reconstruir causalidad.
  • La red demora, reordena, duplica o pierde: un timeout no permite distinguir un nodo caído de una respuesta lenta.
  • Hay fallos parciales: una parte puede funcionar mientras otra falla. El sistema debe decidir con información incompleta.
  • La concurrencia es inevitable: varios participantes operan sobre recursos relacionados sin un orden total natural.
Distribuir compra capacidad, cercanía geográfica y aislamiento de fallos, pero se paga con coordinación. Conviene distribuir solo aquello cuyo beneficio supera ese costo.

Transparencia, con alcance explícito

Decir que un sistema es transparente sin aclarar qué oculta es incompleto. Las dimensiones clásicas son:

  • Acceso: la operación se expresa igual aunque el recurso sea local o remoto.
  • Ubicación: el nombre no revela la dirección física.
  • Migración y relocalización: el recurso puede moverse, incluso mientras se usa, sin cambiar cómo se lo referencia.
  • Replicación: el cliente no elige ni coordina copias.
  • Concurrencia: varios usuarios comparten recursos sin romper invariantes.
  • Fallo: ciertos fallos se enmascaran mediante redundancia o reintentos.
  • Persistencia: se usa igual un objeto temporal que uno reconstruido desde almacenamiento.
La transparencia total no siempre es deseable. Fingir que una llamada remota es local oculta latencia, serialización y ambigüedad ante fallos. Una buena abstracción simplifica el caso normal, pero deja visibles las diferencias que el programa necesita manejar.

Apertura e interoperabilidad

Un sistema abierto publica la sintaxis y la semántica de sus interfaces. Interoperabilidad significa que implementaciones diferentes cooperan. Portabilidad significa que una aplicación puede cambiar de implementación con pocos cambios. Una URL pública no alcanza: también deben estar definidos tipos, errores, compatibilidad, autenticación, orden y semántica de reintentos.

Cómo usar los parámetros en un ejercicio

  1. Fijar requisitos medibles: carga, latencia, disponibilidad, consistencia, recuperación y costo.
  2. Encontrar el recurso limitante y el dominio de fallo.
  3. Elegir un mecanismo para cada requisito, explicando qué sacrifica.
  4. Dibujar componentes, flujos, almacenamiento y límites de responsabilidad.
  5. Recorrer fallos concretos: mensaje perdido, duplicado, nodo lento, caída durante una escritura y partición de red.
Si una venta no puede descontar stock dos veces, “usar una cola” no resuelve por sí solo el requisito. Hay que explicar quién conserva el estado, cómo identifica duplicados, dónde ocurre la operación atómica y qué sucede si el consumidor cae después de guardar pero antes de confirmar el mensaje.

Centralización, distribución y descentralización

Centralizado. Un componente concentra una decisión o un recurso crítico.
Distribuido. El cómputo o los datos viven en más de una computadora.
Descentralizado. Ningún participante tiene control exclusivo y la decisión emerge de la coordinación entre pares.

Distribuido no implica descentralizado: puede haber cien workers gobernados por un único coordinador. Tampoco centralizado implica una sola máquina: un servicio lógico central puede estar replicado. La pregunta útil es qué autoridad, estado o flujo queda concentrado y qué ocurre si deja de estar disponible.

FormaVentajaRiesgoCuándo conviene
Control centralDecisiones simples y observablesCuello de botella o único dominio de falloEscala acotada, coordinación fuerte
JerarquíaAgrega y delega por nivelesLos niveles altos siguen siendo críticosGeografía, agregación, organizaciones grandes
ParesElimina autoridad únicaDiscovery, consenso y seguridad difícilesParticipantes autónomos o alta distribución

Las topologías expresan quién puede comunicarse directamente: estrella simplifica administración pero concentra tránsito; árbol escala agregación pero depende de sus ancestros; anillo limita conexiones pero aumenta el camino; malla ofrece rutas alternativas a mayor costo; bus comparte medio y contención; pipeline encadena etapas con dependencias claras.

Ley de Conway: la arquitectura de un sistema tiende a copiar la estructura de comunicación de la organización que lo construye. Si dos equipos no pueden coordinar cambios, una frontera de servicio entre ellos necesita un contrato mucho más estable que una frontera dentro del mismo equipo.

Virtualización y aislamiento

La virtualización desacopla una carga de trabajo del hardware físico. Esto permite consolidar recursos, reproducir ambientes, aislar fallos y mover capacidad con menos dependencia de una máquina.

Un hypervisor tipo 1 corre sobre el hardware. Uno tipo 2 corre sobre un sistema operativo anfitrión. En contenedores, namespaces aíslan vistas de procesos, red y filesystem; cgroups limitan CPU y memoria; una imagen define capas inmutables; el contenedor agrega una capa efímera de escritura.

En un final, una decisión de diseño completa une requisito, mecanismo y costo. “Replico para disponibilidad” queda incompleto sin indicar qué se replica, cómo se elige una copia, qué consistencia se ofrece y qué fallos cubre.
