U07. Patrones de comunicación; ZeroMQ

Esta unidad sistematiza los patrones de comunicación entre procesos de un sistema distribuido: Request-Reply, Producer-Consumer, Publisher-Subscriber, Pipelines y DAGs. Son el vocabulario con el que se diseña casi cualquier arquitectura de la materia (y de los TPs), y aparecen una y otra vez en los finales como consigna de diseño con pseudocódigo. La segunda parte presenta ZeroMQ, un MOM distribuido (brokerless) que implementa estos patrones directamente sobre sockets.

Request-Reply

Request-Reply. Protocolo de comunicación del modelo cliente-servidor: el cliente envía un Request Message, el servidor lo recibe, procesa la operación y devuelve un Reply Message. Por defecto es sincrónico (bloqueante): el cliente queda bloqueado hasta recibir el Reply.

Quien inicia la comunicación es, por definición, el cliente. En este esquema los ACK son triviales: el Reply funciona como acuse de recibo, porque el servidor no responde nada que no le hayan pedido. El costo es que el tiempo de bloqueo del cliente depende de una operación que no controla: la lógica de negocio del servidor puede tardar poco o mucho, con alta variabilidad (no tarda lo mismo listar 20 mails que insertar mil registros).

El mismo esqueleto sirve para las tres variantes de la unidad: en la operación asincrónica, la 1° parte cambia las etiquetas a Enviar Acción / Encolar acción / Enviar ACK, y la 2° parte a Preguntar Estado / Obtener Estado / Enviar Estado. Cambia el payload, no la topología.

Operación asincrónica con dos Request-Reply

Para no bloquear al cliente durante todo el procesamiento se arma una operación asincrónica encadenando dos Request-Reply sincrónicos:

  1. Encolar la acción: el cliente envía la operación; el servidor no la procesa, solo la encola y responde un ACK inmediato. El contrato implícito es "tu operación fue registrada y eventualmente la voy a procesar", no que ya se ejecutó ni que va a salir bien.
  2. Consultar el estado: más tarde el cliente pregunta por su operación (polling) y el servidor responde el estado: pendiente, en proceso, error o éxito con el resultado.
La gracia es reemplazar una espera larga y de duración impredecible (definida por la lógica de negocio) por dos esperas cortas, uniformes y de baja varianza: encolar y consultar estado son operaciones rápidas y parecidas entre sí, sin importar qué operación de negocio se pidió. El cliente queda libre para hacer trabajo útil entre medio.
En un TP de blockchain, si el envío de un chunk fuera sincrónico de punta a punta, cada cliente quedaría bloqueado hasta que su bloque se mine y persista (tiempo que crece con la dificultad). Con el patrón asincrónico el servidor encola el chunk, responde el ACK enseguida y el cliente consulta después si su bloque ya entró en la cadena.

Si el servidor está saturado (la cola de acciones llena), puede rechazar el Request: el cliente deberá reintentar más tarde. Que el ACK haya llegado garantiza que la acción fue encolada y será procesada.

Estructura de los mensajes

Los mensajes de un protocolo Request-Reply suelen llevar estos campos obligatorios:

  • messageID: distingue Request (0) de Reply (1).
  • requestID: identifica unívocamente al mensaje. Dos alternativas: autoincremental (simple con un solo generador, pero en cuanto hay varios nodos el contador pasa a ser un recurso compartido y se complica) o UUID (128 bits pseudoaleatorios; la probabilidad de colisión es tan baja que en la práctica se asume única, y cualquier cliente puede generarlo sin coordinación).
  • operationID: qué acción u operación se pide.
  • args: argumentos de la operación.

El requestID es la pieza clave: permite consultar el estado de una operación asincrónica y filtrar duplicados. Si el sistema es externo (una API de pagos, por ejemplo), conviene que lo genere el cliente: si lo generara el servidor y el Reply se perdiera, el cliente nunca lo conocería y no podría reintentar de forma segura.

Tolerancia a fallos: timeouts, retries, backoff y jitter

¿Cuánto se espera por un Reply? La respuesta estándar es timeout con retries. Para no martillar a un servidor que ya está en problemas se usa backoff exponencial: el primer reintento al segundo, el siguiente a los 2, luego 4, 8, hasta una cota donde se corta y se asume caída. La lógica: una falla transitoria se resuelve con un retry rápido; si los retries se acumulan, probablemente el sistema está caído y no tiene sentido insistir seguido.

El jitter agrega ruido aleatorio a esos tiempos de backoff. Si diez clientes fueron rechazados en el mismo instante por un servidor sobrecargado y todos usan el mismo backoff determinístico, van a volver a pegarle todos juntos en cada reintento y a fracasar todos juntos otra vez. Dispersar los tiempos alrededor del valor medio rompe esa sincronización accidental (es la política que documenta, por ejemplo, el SDK de AWS).

Semánticas de entrega e idempotencia

¿Qué pasa si se pierde un Request o un Reply? Ojo con el caso sutil: se pierde el ACK, no el Request. El servidor ya encoló la acción, el cliente hace timeout y reenvía, y la acción queda encolada dos veces. Según qué controles haya, la garantía que se obtiene es distinta:

EstrategiaRetry de RequestFiltro de duplicadosGarantía
#1 Sin controlNoNoMaybe (best effort)
#2 Re-ejecuciónSíNoAt Least Once
#3 RetransmisiónSíSíExactly Once
Operación idempotente. Operación cuyo efecto sobre el estado del sistema es el mismo sin importar cuántas veces se ejecute. edad = 40 es idempotente (ejecutarla dos veces deja el mismo estado); saldo = saldo - 100 no lo es (cada ejecución descuenta de nuevo).
At Least Once con operaciones no idempotentes rompe la consistencia: si "extraer $100" queda duplicada en la cola, el cliente ve una sola respuesta pero el servidor descuenta $200. Exactly Once exige retry más filtro de duplicados (típicamente guardando los requestID ya procesados), y ese filtro no es trivial: hay que decidir cuántos IDs retener, por cuánto tiempo, y qué pasa si se pierde esa memoria. La alternativa barata es diseñar operaciones idempotentes, con lo cual At Least Once alcanza.
Qué garantía alcanza depende del caso: para un stream de video, Maybe es suficiente (un pixel perdido no se reintenta, ya pasó el frame); para un GET de lectura, At Least Once no molesta (leer dos veces no cambia el estado); para un pago, se necesita Exactly Once o una operación idempotente con ID de pago generado por el cliente.
Preguntado en finales, casi siempre como consigna de diseño: "Dada una librería basada en request-reply, desarrolle un sistema que distribuya la carga entre N servidores conocidos" (calcular el hash XOR de un archivo por bloques, 2024-07; filtrar logs de Nginx con RegEx entre N nodos, 2025-03), y "Utilizando request-reply, implemente una barrera para que 3 workers se sincronicen" (2024-12). También aparece la teórica "¿RPC resulta excluyente respecto de un modelo Request-Reply?" (2025-07): no, RPC es una abstracción de programación que típicamente se implementa sobre Request-Reply. Conviene tener aceitado el pseudocódigo cliente/servidor con envío, espera de Reply y reparto de trabajo.

Producer-Consumer

Producer-Consumer. Modelo de comunicación por tareas: los producers generan información que es materia prima de un procesamiento posterior, y los consumers esperan la aparición de esa información para procesarla. Cada tarea la toma un solo consumidor.

Admite múltiples productores y múltiples consumidores sobre la misma cola de trabajo. La entrega busca ser equitativa (fairness); en ZeroMQ, por ejemplo, se resuelve con round robin entre consumidores (ver Push-Pull). Es el patrón de las working queues que ya se vieron con RabbitMQ.

Preguntado en finales: "Defina cómo implementar un middleware distribuido que permita a 10 agentes de atención llamar al siguiente número en fila. ¿Dónde almacenaría el último número llamado?". La respuesta esperada es una working queue Producer-Consumer con ACK explícito del agente (si cae sin ACK, el número se re-encola: At Least Once) y persistencia del último número en un sink o base compartida, nunca en la cola, que es transitoria.

Publisher-Subscriber

Publisher-Subscriber. Modelo de comunicación por eventos: los publishers generan elementos de interés y los subscribers esperan la aparición de eventos de su interés para reaccionar. A diferencia de Producer-Consumer, un mismo evento llega a todos los suscriptores interesados, cada uno con su copia.

Entre publishers y subscribers suele mediar un message broker. La ventaja central es el desacoplamiento: sin broker, N publishers y M subscribers necesitarían una malla de conexiones N por M y cada publisher debería conocer a cada interesado; con broker, todos conocen solo al broker, que hace de pasamanos según los intereses declarados. Eso simplifica la comunicación y permite escalar (un publisher puede alcanzar miles de suscriptores sin conocer a ninguno).

Tópicos vs canales

  • Basada en tópicos: cada publicación lleva un tag o tópico (pensarlo como un hashtag) y cada suscriptor declara a qué tópicos se suscribe. El broker entrega cada mensaje a todos los suscriptos a ese tópico.
  • Basada en canales: publicaciones y suscripciones se orientan a canales específicos (por ejemplo, un canal por destinatario). Quien quiere hablarle al suscriptor X publica en el canal de X.

Implementación con MOMs

El ejemplo canónico de la cátedra: Contabilidad (solo subscriber), Ventas (pub-sub: publica ventas, consume stock) y Control de Stock (pub-sub: publica stock, consume ventas).

  • Con un message bus (tópicos): cada mensaje se publica al bus con su tópico (venta o stock) y llega a todos los que escuchan ese tópico: los mensajes de venta llegan a Contabilidad y a Stock; los de stock, a Contabilidad y a Ventas.
  • Con colas (canales): una cola por consumidor; el publicador deposita una copia del mensaje en la cola de cada interesado (el mensaje de venta va a la cola de Contabilidad y a la de Stock). Mismo dominio, modelado distinto: es lo que se hace con RabbitMQ y exchanges en el TP.
No confundir los dos modelos de reparto: en Producer-Consumer los consumidores compiten por las tareas (cada mensaje lo procesa uno solo); en Publisher-Subscriber cada suscriptor del tópico recibe su copia del evento. En finales de diseño se puede usar Pub-Sub "como" productor-consumidor publicando con un tópico por nodo (solo el nodo suscripto a "nodo_i" consume esos mensajes); si se publica sin tópicos que particionen, todos reciben todo y se duplica el trabajo.
Preguntado en finales de forma recurrente: "Utilizando una arquitectura Publisher-Subscriber, calcule la suma de los enteros de un vector de tamaño N optimizando el uso de P procesos" (2022-08), "escriba un sistema que imprima la suma de un gran vector leído por entrada estándar, distribuyendo la carga entre N servidores conocidos" (2025-02) y "calcule el promedio de ventas recibidas en streaming con ventanas de 1M de registros" (2025-07), siempre con pseudocódigo. El truco típico: particionar con un tópico por worker y un tópico de resultados al que se suscribe quien agrega. También: "Describa cómo implementaría un middleware de comunicación de grupo con tres grupos fijos y membresía dinámica", que se resuelve con Pub-Sub por tópicos más un servicio de membresía.

Pipelines

Pipeline (Pipes and Filters). Estilo en el que los datos de entrada forman un flujo que atraviesa una secuencia de filters (o processors) conectados entre sí: cada filter aplica una transformación y pasa el resultado al siguiente, desde un source hasta un sink.

Está inspirado en el procesamiento de señales y es la esencia de los pipes de Unix: cat in | grep pattern | sort | uniq > out es un pipeline con un source (cat), tres etapas de transformación y un sink (la redirección a out).

Modelos de procesamiento: worker por filter vs worker por item

  • Worker por filter: cada etapa tiene su propia unidad de procesamiento; los ítems se encolan entre etapas y cada worker procesa su etapa y pasa el ítem a la siguiente. Mejor throughput global: no hay una cota dada por la cantidad de workers "acompañando" ítems, y cada ítem espera solo a la etapa que tiene delante. Permite escalar horizontalmente la etapa que sea cuello de botella.
  • Worker por item: un worker toma un ítem y lo acompaña por todo el pipeline aplicándole los filters paso a paso. Mantiene todo el contexto del ítem en la misma unidad de procesamiento (buena afinidad si el procesamiento depende fuertemente del contexto), pero con P workers no se procesan más de P ítems en simultáneo y la latencia por ítem incluye el pipeline entero.

El throughput máximo del pipeline queda limitado por la etapa más lenta: una vez lleno, el pipeline avanza al ritmo del stage que más tarda. De ahí que el análisis de cuellos de botella indique qué etapa escalar.

Etapas secuenciales y paralelas

  • Paralela: cada ítem es independiente de anteriores y posteriores, así que la etapa admite varias instancias procesando a la vez (un map que multiplica por 2 no depende del orden).
  • Secuencial: no puede procesar más de un ítem a la vez (importa el orden o hay estado compartido). Puede devolver los ítems ordenados o desordenados.

Ventajas: algoritmos online e información infinita

  • Algoritmos online: el procesamiento arranca antes de que estén todos los datos disponibles.
  • Información infinita: permite trabajar con flujos ilimitados usando memoria constante: el procesamiento está encadenado y solo se necesita un buffer mínimo por etapa. Para streams sin fin se opera por ventanas (por ejemplo, cada 1000 elementos se emite un resultado parcial) o con algoritmos online que mantienen un estado acotado (un promedio que se actualiza incrementalmente aproxima el promedio de todo lo visto sin guardar los datos).

Pipes y filters como artefactos de programación

El patrón tiene solo dos conceptos, y la pregunta de final es siempre la misma: ¿en qué se traducen al escribir el sistema? La respuesta corta: el filter es una unidad de ejecución (proceso, thread o contenedor) que corre una función de transformación, y el pipe es un canal de comunicación con buffer entre dos de esas unidades. Todo lo demás son variantes de implementación de esos dos artefactos.

Filter, en artefactos:

  • Una función de transformación pura: recibe un ítem, devuelve cero, uno o varios ítems de salida. Es la unidad conceptual (un map, un filter en el sentido de descartar, un flatMap que abre un ítem en varios).
  • Una unidad de ejecución que hostea esa función y corre un loop recibir, transformar, emitir: un thread, un proceso, o un contenedor. En la práctica de la materia es un worker, y una etapa es un pool de workers idénticos (ver worker por filter).
  • Visto desde la comunicación, cada filter es al mismo tiempo consumidor de la cola de entrada y productor de la cola de salida: producer-consumer encadenado. Los extremos son casos degenerados: el source solo produce (lee de un archivo, un socket, un stream externo) y el sink solo consume (persiste en una base, escribe un archivo, dispara una alerta).
  • En Unix el filter es literalmente un programa que lee de stdin y escribe en stdout: grep, sort, uniq. Esa es la definición original y sigue siendo la mejor intuición.
# filter tipico: worker de una etapa, stateless
entrada = mom.consumidor("reviews.norm")
salida  = mom.productor("reviews.scored")
for msg in entrada:
    r = deserializar(msg)
    r.score = puntuar(r.texto)          # la funcion de transformacion
    salida.enviar(serializar(r), clave=hash(r.producto))
    entrada.ack(msg)                    # ack recien despues de emitir
Conviene que el filter sea stateless (todo lo que necesita viene en el ítem) por tres razones: cualquier réplica puede procesar cualquier ítem, así que el pipe puede repartir por round robin y la etapa escala horizontalmente sumando instancias; si una instancia muere no hay estado que recuperar, alcanza con que el ítem sin ACK vuelva a la cola y lo tome otra; y el ítem se vuelve la unidad de reintento, con lo cual la etapa es fácil de hacer idempotente (ver semánticas de entrega). Cuando la etapa necesita estado (contar, promediar, joinear), la salida barata es particionar por clave: cada instancia es dueña exclusiva de un subconjunto de claves, y así una etapa con estado se sigue paralelizando.

Pipe, en artefactos: cualquier canal unidireccional con buffer que desacople la velocidad de las dos etapas que conecta. Las opciones concretas, de menos a más garantías:

ConceptoArtefactoEjemploGarantías
FilterProceso, thread o contenedor con loop recibir, transformar, emitir (worker)grep pattern; un contenedor parser replicado 5 vecesSi es stateless, replicable y reiniciable sin recuperar nada
Filter con estadoWorker con estado local más particionado por clave del ítemAgregador que promedia por productoNo se puede replicar libremente: hay que rutear cada clave siempre a la misma instancia
PipePipe del sistema operativo (anonymous pipe o FIFO, ver IPCs)cat in | grep pattern | sort > outBuffer en memoria del kernel, una máquina, sin persistencia: si un proceso muere se pierde lo que estaba en vuelo

Error típico en el final: contestar "los pipes son los pipes de Unix" y quedarse ahí. Un pipe del SO no cruza la frontera de la máquina, así que en un sistema distribuido el pipe es siempre otra cosa: una cola de un MOM, un socket, o un stream de un framework. Y la elección no es cosmética: cambia las garantías. Con un pipe del SO, si el proceso de la etapa 2 muere, lo que estaba en el buffer se perdió y el pipeline se corta; con una cola durable de un MOM, los ítems siguen ahí cuando la etapa se relevanta, y otro worker los toma.

Sistema supuesto: análisis de reseñas de un e-commerce en streaming. Entran reseñas (producto, usuario, texto, estrellas) por un stream infinito y hay que publicar, cada 100.000 reseñas, el promedio de sentimiento por producto. Pipeline de cinco etapas, todas en contenedores, todos los pipes son colas durables de un MOM:

  • Ingestor (source, 1 instancia): recibe las reseñas del front, valida el formato mínimo, serializa a JSON y produce a la cola reviews.raw. No es replicable sin más porque es el punto de entrada, pero tampoco hace trabajo pesado.
  • Normalizador (filter stateless, N instancias): consume reviews.raw, baja el texto a minúsculas, saca HTML y emojis, descarta reseñas vacías (un filter que además filtra en el sentido literal) y produce a reviews.norm.
  • Clasificador de sentimiento (filter stateless, M instancias): consume reviews.norm, calcula un score en el rango -1 a 1 y produce a reviews.scored usando hash(producto) como clave de ruteo. Es CPU bound y la etapa más lenta, así que es la que define el throughput del pipeline entero.
  • Agregador (filter con estado, K instancias particionadas): cada instancia recibe solo los productos cuyo hash le corresponde, mantiene (suma, cuenta) por producto en memoria y cada 100.000 reseñas emite los promedios de su partición a reviews.out. Es la única etapa que no se puede escalar simplemente sumando instancias: escalarla implica repartir de nuevo las claves.
  • Sink (1 o pocas instancias): consume reviews.out y persiste el ranking en la base que sirve al dashboard.

Cómo escala cada etapa por separado: se mide la profundidad de cada cola. Si reviews.norm crece sin parar, el cuello está en el clasificador: se levantan más instancias de esa sola etapa (de 4 a 12 contenedores) sin tocar una línea del resto, porque ninguna etapa conoce cuántas instancias tienen las demás: solo conocen el nombre de sus colas. Si crece reviews.raw, el cuello es el normalizador. Si crece reviews.out, el problema es la base y hay que mirar el sink. El pipeline no puede ir más rápido que su etapa más lenta, así que el único escalado que sirve es el de la etapa que está saturada.

Qué pasa si muere un worker: las etapas stateless no pierden nada, el ítem sin ACK vuelve a la cola y otra instancia lo reprocesa (At Least Once). El agregador sí pierde su ventana parcial, y ahí hay que decidir: aceptar la pérdida de una ventana, checkpointear el estado periódicamente, o delegar el problema a un framework como Flink, que hace exactamente eso.

Preguntado en finales de forma casi literal: "En una arquitectura de 'Pipes and Filters', ¿cómo se implementan sus 2 conceptos principales (pipes y filters) en artefactos de programación? Dé un ejemplo concreto dentro de un sistema distribuido supuesto" (2025-07-03). Lo que se espera: filters como componentes de procesamiento independientes (funciones o servicios que toman un input, lo transforman y emiten un output, hosteados en procesos, threads o contenedores) y pipes como los canales que los conectan (colas de mensajes, streams o buffers), más un ejemplo desarrollado de punta a punta. Un ejemplo mínimo y fácil de recordar: procesamiento de video, donde un filter decodifica, un pipe pasa los frames crudos al filter que aplica la marca de agua, y otro pipe lleva el resultado al filter de compresión.

DAGs

DAG (Directed Acyclic Graph). Grafo dirigido sin ciclos que modela un flujo de datos: los nodos son tareas y las aristas el flujo de información (una arista de A a B significa que B necesita el resultado de A). Acíclico: ningún nodo tiene un camino que salga de él y vuelva a él.

Ventajas de modelar el cómputo como DAG:

  • Representación natural de dataflows: el pipeline es un caso particular (lineal) de DAG.
  • Paralelización: las dependencias explícitas muestran qué tareas pueden correr en simultáneo. Con dos procesos, en el DAG de la figura A corre primero, luego B y D en paralelo, y E cuando C y D terminan. Conecta con el modelo work-span y el camino crítico (la cadena secuencial más larga de tareas, que acota el speedup) vistos en paralelización.
  • Lazy loading: solo se ejecutan los nodos requeridos por dependencias del resultado pedido. Si solo interesa E, las ramas que no llegan a E no se computan; si B falla, no tiene sentido ejecutar lo que dependía de B.
  • Reutilización: un resultado intermedio compartido por varias ramas se calcula una sola vez.

Dependencias, wait-for y deadlocks

Los DAGs también sirven para modelar dependencias entre procesos (grafos wait-for: una arista de Pi a Pj significa que Pi espera un recurso que tiene Pj). Toda dependencia implica posibilidad de bloqueo; si el grafo de espera tiene un ciclo, hay posibilidad de deadlock: Pi espera a Pj, Pj a Pk y Pk a Pi, nadie avanza. Mientras el grafo de espera siga siendo un DAG (sin ciclos), el deadlock es imposible; detectar un ciclo permite recuperarse (matar un proceso, soltar un lock) o rediseñar el sistema para prevenirlo.

Ejemplo: TensorFlow como constructor de DAGs

TensorFlow es un framework donde el programa no ejecuta operaciones al escribirlas: las declara y construye un DAG. b = tf.negative(a), c = tf.abs(b), d = b * c, e = tf.abs(d) arman un grafo donde cada operación es un nodo que depende de sus insumos; recién session.run(e) dispara la ejecución, y solo de los nodos que E necesita. La sesión puede correr ese mismo DAG en una máquina o en un cluster: el usuario define las operaciones y el framework decide dónde ejecutarlas. Además el enfoque es reactivo: si a es un stream que va generando valores, los nodos aguas abajo van actualizando sus resultados a medida que llegan datos, como un pipeline.

ZeroMQ: MOM distribuido

ZeroMQ (ZMQ). Librería de mensajería descripta por sus autores como "sockets on steroids": sockets de alto nivel, altamente performantes (núcleo optimizado en C), pensados para construir middlewares brokerless (descentralizados, sin broker central obligatorio). La serialización de los mensajes queda a cargo del usuario, y provee soporte nativo para los patrones de esta unidad: Request-Reply, Publisher-Subscriber, Parallel Pipeline y patrones avanzados.

Existen alternativas más modernas de los mismos autores (nanomsg, NSQ, NNG), pero con los mismos conceptos. En ZMQ cada socket tiene un tipo que define su rol en un patrón, y los sockets de un proceso comparten un contexto (el contexto es, entre otras cosas, el nexo que permite que dos threads del mismo proceso se comuniquen).

El mismo programa sirve para los tres mundos: pasar de multicomputing a multiprocessing o multithreading es cambiar tcp://host:5555 por ipc://nombre o inproc://nombre en el bind/connect, sin tocar el resto del código. Esa abstracción de la complejidad es el argumento de venta del middleware (con el costo de que, cuando algo se rompe, debuggear la magia es más difícil).

Request-Reply en ZMQ (REQ/REP)

Es el cliente-servidor convencional, "aunque no tanto":

  • No existe la primitiva accept: el bind del servidor funciona como bind + accept. No hay un socket por cliente; el servidor hace recv y le llegan mensajes de cualquier cliente conectado.
  • send es no bloqueante, y el cliente no necesita que el servidor esté corriendo para enviar: ZMQ buferea. Under the hood hay I/O threads (1 thread por GB/s de tráfico) que despachan los mensajes cuando el canal está disponible. Si el servidor se levanta más tarde, la comunicación fluye sola.
# servidor                          # cliente
context = zmq.Context()             context = zmq.Context()
socket = context.socket(zmq.REP)    socket = context.socket(zmq.REQ)
socket.bind("tcp://*:5555")         socket.connect("tcp://server:5555")
while True:                         for i in range(10):
    msg = socket.recv()                 socket.send(b"Hello")
    socket.send(b"World")               reply = socket.recv()
El buffering tiene límites y la magia no es simétrica: si el servidor muere abruptamente mientras un cliente espera su Reply, al relevantarse el servidor ese socket cliente no se restablece solo; ese caso hay que manejarlo a mano. Y el buffer del emisor es finito: acumular mensajes sin receptor termina explotando.

Producer-Consumer y Pipeline (PUSH/PULL)

Los sockets PUSH y PULL marcan el rol de cada extremo en la comunicación por tareas: PUSH envía, PULL recibe. Admite 1 PUSH hacia N PULL (repartir trabajo) y N PUSH hacia 1 PULL (juntar resultados); encadenando productores-consumidores se arma un pipeline completo.

Lo poderoso del patrón: el ventilator no sabe cuántos workers hay ni el sink cuántos le escriben. Pasar de 3 a 20 workers no cambia una línea de código, y el speedup se observa directo (una carga de 5 segundos de trabajo se completa en unos 2 con 3 workers).

"Fairness" en ZMQ significa round robin estricto: primer mensaje al primer worker, segundo al segundo, y así. No hay balanceo por carga ni por disponibilidad: si un worker es 10 veces más lento, igual le siguen llegando mensajes y frena la simulación entera. Comparar con RabbitMQ, donde el prefetch y los ACKs permiten que cada worker tome trabajo según su disponibilidad.

Publisher-Subscriber en ZMQ (PUB/SUB y XPUB/XSUB)

  • Un socket PUB publica mensajes con el patrón id campo1 campo2 ... campoN: el primer token es el ID del evento (el tópico).
  • N sockets SUB se suscriben a los IDs que quieren recibir (setsockopt(SUBSCRIBE, id)); la suscripción funciona por prefijo del mensaje y puede cancelarse en cualquier momento.
  • Cada mensaje se entrega a todos los sockets suscriptos a ese ID.
  • Semántica invertida respecto de REQ/REP: el PUB hace bind (actúa como servidor) y además es quien envía.
El ejemplo de la cátedra publica mediciones de clima con un zip code (1, 2 o 3) como ID; cada subscriber se suscribe a un zip code y solo recibe los mensajes de su zona, calcula un promedio tras 5 mensajes y termina.
Si nadie está suscripto, los mensajes publicados se pierden: un subscriber que se conecta tarde no ve lo publicado antes, y uno que se cae y vuelve no recupera los mensajes intermedios. Estos edge cases (¿bloqueo al recibir?, ¿se encolan mensajes sin suscriptores?) varían de framework a framework y hay que verificarlos en la documentación.

¿Múltiples publishers y múltiples subscribers? Patrón XPUB-XSUB: un proxy con un socket XSUB (que se suscribe a todos los publishers) y un XPUB (al que se suscriben todos los subscribers) redirige de uno a otro, mimetizando el message broker centralizado del modelo Pub-Sub.

Router-Dealer: construir un broker

Para enrutar múltiples clientes contra múltiples servidores Request-Reply, ZMQ ofrece los sockets ROUTER y DEALER, con los que se construye un broker centralizado cuando el diseño lo pide:

  • ROUTER (frontend, mira a los clientes): agrega al mensaje recibido un ID de destinatario, taggeando de dónde vino cada mensaje para poder devolver el Reply al cliente correcto.
  • DEALER (backend, mira a los servidores): rutea los mensajes de forma fair entre los servidores y propaga el ID de origen.
  • Ambos reciben de múltiples sockets a la vez y son asincrónicos: el proxy usa un poller (abstracción de la syscall poll, equivalente al select de las primeras clases) para esperar mensajes de frontend y backend y reenviar en ambas direcciones.
frontend = context.socket(zmq.ROUTER); frontend.bind("tcp://*:5559")
backend  = context.socket(zmq.DEALER); backend.bind("tcp://*:5560")
poller = zmq.Poller()
poller.register(frontend, zmq.POLLIN)
poller.register(backend, zmq.POLLIN)
while True:
    socks = dict(poller.poll())
    if frontend in socks: backend.send_multipart(frontend.recv_multipart())
    if backend in socks:  frontend.send_multipart(backend.recv_multipart())

Clientes y servidores hacen ambos connect al proxy (los dos actúan "de cliente" del broker) y el taggeo de IDs queda enmascarado: para ellos es transparente que hay un router-dealer en el medio. Como el proxy lee cada mensaje, también se puede reemplazar el ruteo fair por un ruteo propio basado en tags del mensaje.
