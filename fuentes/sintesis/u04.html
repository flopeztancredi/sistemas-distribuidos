U04. Layers y tiers, interfaces, protocolos y REST

Todo sistema distribuido se construye dividiendo un problema grande en subproblemas: capas lógicas (layers) y físicas (tiers) organizan esa división, las interfaces definen los contratos entre las partes, y los protocolos y formatos de mensaje definen cómo viajan los datos entre nodos. La unidad cierra con REST, el estándar de facto de la industria para exponer servicios sobre HTTP, y con el versionado de APIs. Es una unidad muy preguntada en finales: diseño de protocolos binarios vs texto plano, layers vs tiers y orientación de contratos aparecen una y otra vez.

Arquitecturas de capas

Si un sistema se plantea como una sucesión de problemas pequeños, hay mucha más chance de resolver bien cada uno por separado. Las arquitecturas de capas hacen exactamente eso:

  • Dividen el problema en subproblemas.
  • Fomentan el uso de interfaces: la línea delgada donde una capa toca a la otra e intercambian datos es, conceptualmente, una interfaz.
  • Permiten intercambiar componentes reutilizando conectores y protocolos ya definidos.
Layer (capa lógica). Agrupación lógica de componentes y funcionalidades de un sistema. No dice nada sobre dónde corre el código.
Tier (capa física). Describe la distribución física de componentes y funcionalidad: cada tier es un nodo, un servidor, un elemento físico de despliegue.
Layers y tiers son dos vistas distintas del mismo sistema, igual que las vistas de un modelo de documentación (unidad 3): el layer responde "cómo está organizado lógicamente el código", el tier responde "en qué máquinas se despliega". La distinción es histórica pero sigue siendo valiosa: usar la palabra precisa (lógico vs físico) evita malentendidos al comunicar una arquitectura.
Preguntado en finales: "Diferencie los conceptos de Capas Lógicas (Layers) y Niveles de Despliegue (Tiers) en el diseño de arquitectura de software. Dé un ejemplo de una arquitectura de 3-Tiers" (compilado de preguntas de finales de la cátedra). La respuesta esperada: layers = organización lógica del código para separar responsabilidades; tiers = distribución física en nodos; ejemplo 3-tier: UI en el dispositivo del cliente, lógica en un servidor de aplicaciones, base de datos en un servidor separado.

Layers: comunicación, jerarquía y responsabilidades

Los layers se disponen en dos sentidos:

  • Capas verticales: apiladas con jerarquía. La capa N se apoya en la N-1 para cumplir su funcionalidad: la capa inferior ofrece funcionalidad más básica y específica, y la superior la compone para armar funcionalidad de mayor complejidad.
  • Capas horizontales o transversales: cruzan y tocan a todas las verticales (típicamente seguridad y auditoría).

La disposición vertical define los canales de comunicación posibles:

  • Downcall: la capa N llama hacia abajo (N-1), con o sin respuesta. Es el caso normal.
  • Upcall: la capa N llama hacia arriba (N+1). Es excepcional y problemático.

Upcalls y dependencias circulares

¿Por qué el upcall trae problemas? Si el código de la capa N importa a la N-1 y el de la N-1 importa a la N, se arma una dependencia circular: molesta para los despliegues, hace confuso quién depende de quién, y ninguna de las dos capas puede existir sin la otra. La pregunta que hay que hacerse es si esa circularidad es real: si no se puede delimitar la responsabilidad de cada capa porque sus elementos "hablan demasiado" entre sí, probablemente no haya dos capas sino una sola con más cohesión, y conviene que una absorba a la otra.

Cuando la separación sí tiene sentido y la capa inferior necesita avisar algo hacia arriba, la solución típica es un callback o event handler: la capa superior registra una función en la inferior, y cuando en la capa de abajo ocurre un evento, invoca ese callback sin saber qué hay del otro lado. La capa de abajo no importa código de la de arriba: solo emite un evento.

# capa N-1: no conoce a la capa superior
def register_callback(cb):
    global callback
    callback = cb

def al_ocurrir_evento(datos):
    if callback:
        callback(datos)   # upcall sin dependencia circular

# capa N: se registra como interesada
register_callback(mi_handler)

Un modelo lógico típico

Cada layer debe ser un módulo con responsabilidades limitadas, coherencia y cohesión: un conjunto acotado de cosas que hace y hace bien. El modelo lógico que encaja en la mayoría de las aplicaciones web actuales es:

  • Persistence: acceso a los datos, comunicación con la base de datos, storage.
  • Core Business: entidades y modelo de negocio; se apoya en Persistence.
  • Services: compone entidades básicas en operaciones complejas. Se intenta que cada servicio sea atómico: una única transacción desde que se lo invoca hasta que retorna.
  • API y Presentation: puntos de entrada. Presentation define los boundaries con los que interactúa el usuario; API expone servicios a aplicaciones externas (la propia interfaz gráfica puede consumir la API, o puede hacerlo un tercero).
  • Security y Audit: capas transversales que verifican roles, accesos y registran actividad antes de responder, sin ser parte de la lógica del servicio en sí.

Otra forma de organizar layers es la Onion Architecture (Clean Architecture, de Jeffrey Palermo y Robert Martin): capas concéntricas con el dominio en el centro y las dependencias apuntando siempre hacia adentro.

Tiers: 2-tier, 3-tier y despliegue de layers

En un diagrama de tiers cada caja es un nodo físico, y las líneas entre nodos se pueden anotar con el protocolo con que se hablan. La cantidad de tiers dio nombre a arquitecturas clásicas:

  • 2-Tier: una base de datos central (un tier) y aplicaciones cliente instaladas en cada computadora (el otro tier) que abren conexión contra la base, extraen datos y los muestran. Con este modelo la industria sobrevivió muchos años; toda empresa tuvo alguna vez su base centralizada y un "clientito" instalado en cada máquina. A veces parte de la lógica vivía en la base (stored procedures, PL/SQL).
  • 3-Tier: la evolución: la lógica de negocio se separa a un servidor propio. Queda un cliente "tonto" que recibe la información ya procesada, un tier de lógica de negocio y un tier de base de datos. Es el modelo de las aplicaciones web clásicas: browser con HTML y algo de JavaScript, servidor PHP, base MySQL.

Los dos modelos se integran: los layers (paquetes lógicos) se despliegan sobre los tiers. El ejemplo de la cátedra reparte los layers en cuatro tiers: un Client Tier con el WebClient, un Application Tier con Presentation y API, un Business Logic Tier con Services, Core Business y Persistence, y un Database Tier al que accede el anterior. Security y Audit no viven en un tier propio: son layers transversales que se despliegan en los dos servidores.

Ojo con dónde cae Services: va con Core Business y Persistence en el Business Logic Tier. El Application Tier expone la aplicación (Presentation y API); componer entidades en operaciones transaccionales ya es lógica de negocio. Confundirlos es el error clásico en el ejercicio de repartir layers sobre tiers.
Si un mismo layer (por ejemplo Audit) se despliega en dos tiers, hay que desplegar la misma versión en ambos. Un despliegue con versiones distintas de un componente compartido en distintos nodos puede hacer que el sistema distribuido "no ande muy bien": acá empieza la complejidad real de las aplicaciones web como sistemas distribuidos.

Interfaces y contratos

Interfaz. Elemento que permite la comunicación entre dos o más componentes, servicios o sistemas definiendo un contrato: expone solo la parte pública del sistema y esconde la implementación privada.

Consecuencias directas de esa definición:

  • Diferentes contratos permiten diferentes clientes.
  • La implementación puede modificarse sin avisarle a nadie, mientras el contrato se siga cumpliendo.
  • Un cambio de contrato implica una nueva versión de la interfaz.

Hay dos ámbitos de interfaz:

Inter-aplicacionesIntra-aplicación
Qué esApplication Programming Interfaces (APIs): el punto de acceso para que una aplicación que vive por sí sola sea reutilizada por otra sin reescribir su funcionalidad.Patrones como Facade o Mediator, e interfaces entre layers. La aplicación es una sola: no tiene sentido desplegar un pedacito suelto.
EjemplosCliente de consola contra un web server, JS del navegador contra un servidor, servicio contra servicio.Layer 2 consultando Layer 1, mensajes entre objetos locales (o remotos, si el despliegue tiene muchos nodos).

Dos problemas guían el diseño de todo contrato:

  • El software es difícil de integrar: si expongo todos los puntos del sistema sin esconder nada, la complejidad de integrar crece exponencialmente con la cantidad de elementos expuestos. Mejor interfaces pequeñas que van al grano; si quedan chicas, se publica una nueva versión.
  • El software es difícil de cambiar: si un sistema quedó altamente acoplado a una API y esta cambia, hay un problema grande. Hay una línea fina entre una interfaz flexible y una cerrada; y querer contemplar todo por años mete ruido y complica el uso.

Orientación del contrato: entidades vs procesos

Orientado a entidadesOrientado a procesos
ObjetivoDesacoplamiento entre sistemas, flexibilidadAlta performance
AcoplamientoBajoComponentes altamente acoplados
FuncionalidadEstándar (CRUD sobre recursos)Diversa (acciones, procesamiento)
Forma del endpointLa URI nombra una entidad; la acción la da el verbo HTTPLa URI describe la acción
La API de Wikipedia/Wikimedia mezcla ambos estilos. Orientados a entidades: GET /page/title/{title}, POST /page/html/{title}, GET /feed/featured/{yyyy}/{mm}/{dd} (la entidad "page" o "feed" y el verbo dicen todo). Orientados a procesos: POST /transform/html/to/wikitext/{title} (procesa y convierte formato), POST /media/math/check/tex (valida una fórmula LaTeX). No es que Wikipedia no sepa escribir interfaces: es que no siempre se puede ser purista con una sola orientación.
Preguntado en finales: "El contrato de una interfaz puede estar orientado a entidades o a procesos. Describa ambos modelos y dé un ejemplo de al menos dos endpoints de cada estilo para una API" (2025-02). Conviene tener listos dos endpoints de cada estilo (por ejemplo GET /users/{id} y POST /products vs POST /search y POST /transform/...) y las palabras clave: entidades = desacoplamiento y flexibilidad, procesos = acoplamiento y performance.

Clasificación de APIs

  • Web APIs: REST based (HTTP + JSON, hoy las más extendidas) y Web Services based (HTTP + SOAP, un XML de estructura muy fuerte para intercambio de objetos, con tooling propio para descubrir servicios).
  • Remote APIs: servicios TCP/UDP custom; orientadas a objetos (CORBA, Java RMI, hoy en deprecación); orientadas a procedimientos (RPC, y su regreso moderno como gRPC de la mano de Google).
  • Library-based / frameworks: la Java API (gracias a un contrato firme pueden convivir implementaciones como OpenJDK y Oracle JDK), la Android API.
  • OS related: POSIX (un SO POSIX garantiza un mínimo de funciones: abrir, cerrar, saltear caracteres en un archivo, etc.; por eso Docker pudo apuntar "a sistemas POSIX" sin importar qué hay debajo), WinAPI.

Protocolos

Ejemplo: el modelo HTTP

HTTP es un modelo cliente-servidor y request-reply: el cliente siempre pide, el servidor siempre responde; el servidor nunca inicia un pedido hacia el cliente. Y es sin estado (del lado del servidor): una invocación no sabe nada de la siguiente, por lo que el cliente debe mantener el estado y referenciar en cada pedido a qué se refiere (por ejemplo, borrar indicando el id del recurso, no "el que seleccioné recién").

GET https://en.wikipedia.org/wiki HTTP/1.1
Host: www.example.com
Accept: text/html,application/xhtml+xml;
Accept-encoding: gzip, deflate, br
Accept-language: en-US,en;q=0.9,es;q=0.8

HTTP/1.1 200 OK
Content-encoding: gzip
Content-language: en
Content-length: 18558
Content-type: text/html; charset=UTF-8

<!DOCTYPE html> ...

El request lleva un verbo (GET, POST, PUT, ...), un path (con argumentos opcionales tras ?) y headers (Host, qué tipos de respuesta acepto, qué encoding, qué idioma). La respuesta trae un código de retorno (200 = OK), el encoding e idioma usados, el content type y la longitud del body en bytes: contando esa cantidad el cliente decodifica el body.

Responsabilidades por capa y PDUs

En un stack tipo TCP/IP (Application, Transport, Internet, Network Access) cada capa habla lógicamente con su par del otro nodo, pero HTTP solo existe en Application: las capas de abajo no saben nada de HTTP. Cada capa toma lo que le pasa la capa superior, lo mete en el body de su propio protocolo y le agrega sus headers. El mensaje crece a medida que baja.

PDU (Protocol Data Unit). La unidad de datos de cada protocolo: el paquete que una capa entrega a la inferior para ser encapsulado.

Formas de encapsular PDUs entre capas:

  1. Encapsulación exacta: la capa inferior reserva en su payload el espacio exacto para el mensaje de la superior (ej: payload dentro de TCP header, dentro de IP header, dentro de Net header).
  2. Segmentación: el mensaje supera el límite de la capa inferior y se corta en varios paquetes. Cada segmento repite headers: más overhead y una aplicación más chatty.
  3. Batching (blocking): la capa inferior espera varios paquetes de la superior y los agrupa en un solo bloque, amortizando headers.
El concepto de PDU no es exclusivo de TCP: es universal entre las capas que uno mismo arma (Services puede tener su PDU que Communication encapsula). Y la segmentación pasa "sola": mandar una imagen de 32 MB en un solo chunk sobre UDP significa que se segmenta por debajo y, si se pierde un pedacito, se pierde la imagen. Una aplicación debe considerar sobre qué está parada y qué calidad de servicio le da la capa inferior.

La gracia de las capas es la abstracción: FTP, HTTP y SMTP se basan en TCP; DNS usa UDP para agilizar; y todos se apoyan en IP, que al cortar la visibilidad hacia abajo permite implementarse sobre cualquier network access (Ethernet, fibra, Token Ring). Mientras la capa de abajo cumpla su contrato, se la puede cambiar y todo sigue andando.

Longitud de paquete: bloques fijos, dinámicos y mixtos

  • Bloques fijos: cada dato tiene longitud fija. Fácil de serializar, pero subóptimo con tipos de longitud variable como strings.
  • Bloques dinámicos: un separador delimita comienzo y fin de campo, o un campo de longitud indica cuánto ocupa el valor. Pequeño overhead por los bytes extra.
  • Esquema mixto: los parámetros fijos (integers) van sin delimitador ni longitud; los variables llevan delimitador o longitud.
TLV (Type-Length-Value): todo parámetro se codifica como Type (tipo de dato, tamaño fijo), Length (longitud del value, tamaño fijo) y Value (dato, tamaño variable, admite subtipos). Con un mini protocolo donde 01 = integer, 02 = string, 03 = dirección (compuesto de 03.01 calle string, 03.02 número integer, 03.03 unidad string), la dirección "Alsina 2B" se serializa: 
03 11                          # Direccion, 0x11 bytes
  01 06 41 6c 73 69 6e 61      # Calle: "Alsina" (6 bytes)
  02 04 00 00 00 02            # Numero: 2 (int de 4 bytes)
  03 01 42                     # Unidad: "B" (1 byte)
TFTP combina bloques fijos y delimitadores: el paquete Read/Write lleva opcode (2 bytes fijos), filename (string terminado en un byte 0) y mode (string + byte 0); el paquete Data lleva opcode 3, block# (2 bytes) y hasta 512 bytes de datos; el ACK lleva opcode 4 y block#. El fin de archivo se señala con un bloque de datos de menos de 512 bytes: un archivo de 513 bytes viaja como un bloque de 512 y uno de 1; uno de exactamente 512 obliga a mandar un segundo bloque de 0 bytes para indicar que terminó.
Preguntado en finales, con variantes: "Defina 2 protocolos distintos para la transmisión de paquetes considerando un registro que posee un int y un arreglo de flotantes / un struct con email:str y nacimiento:date / un float y una lista de strings. Compare ventajas y desventajas de cada protocolo" (2024-07, 2025-02, 2025-12). La estructura de respuesta es siempre la misma: protocolo 1 texto plano (JSON: fácil de implementar y debuggear, serializadores ubicuos, ocupa más), protocolo 2 binario (TLV o esquema mixto con longitud al inicio: bytes exactos, serialización inmediata, pero hay que implementar encoder/decoder por lenguaje, salvo que se use un IDL tipo Protobuf/gRPC que autogenera stubs).

Sincronización de señales y mensajes sincrónicos vs asincrónicos

En ciertos protocolos hay que saber dónde empieza una señal para entender la secuencia. Ejemplo de bajo nivel: el sensor DHT11 (humedad y temperatura) manda por un pin una señal de sincronismo inicial y luego 40 bits de datos (byte entero y decimal de humedad, byte entero y decimal de temperatura, checksum).

En cuanto a la interacción, un intercambio puede ser sincrónico (el cliente queda idle esperando la respuesta antes de continuar) o asincrónico (el cliente sigue activo tras enviar el request y procesa la respuesta cuando llega). Este eje va a reaparecer en middlewares y MOMs.

Caso real: protocolo custom con múltiples canales

Una bolsa de comercio recibe órdenes de muchos operadores distribuidos, con picos de tráfico donde importa el throughput. Solución: cada trader contrata dos canales dedicados (fibras de dos carriers) y manda cada paquete duplicado por ambos, con un protocolo UDP liviano y números de serie. El servidor procesa el primero que llega y descarta el duplicado del otro canal. Si un paquete se pierde en un canal, llega por el otro: la redundancia cubre la enorme mayoría de las pérdidas sin retransmitir. Para el caso raro en que se pierden ambos, hay un canal TCP lento por el que el exchange pide "retransmitime el paquete N". Así el 99% de los casos corre a máxima velocidad y la excepción se resuelve sacrificando throughput solo un instante. Moraleja: los protocolos se diseñan a medida del problema, combinando canales y garantías.

REST

REST (Representational State Transfer). Estilo de arquitectura basado en entidades (web resources), donde cada recurso se representa con una URI, HTTP/HTTPS es el protocolo de comunicación, JSON/XML el formato de serialización, y los cambios de estado se hacen con operaciones CRUD mapeadas a verbos HTTP.
OperaciónVerbo HTTPEquivalente SQL
CreatePOSTINSERT
ReadGETSELECT
UpdatePUTUPDATE
DeleteDELETEDELETE
Idempotencia de los verbos. PUT es idempotente: repetir la misma actualización N veces deja el objeto igual que hacerla una vez. GET también: 100 GETs seguidos devuelven lo mismo. POST no es idempotente: ejecutarlo N veces crea N entidades. Esto importa muchísimo al reintentar operaciones (retries ante timeouts): un GET o PUT se puede repetir tranquilo; un POST repetido duplica. La idempotencia vuelve como concepto central en tolerancia a fallos y mensajes duplicados.

Principios de arquitectura

REST persigue alta performance, escalabilidad y confiabilidad mediante:

  • Arquitectura cliente/servidor.
  • Cacheability: las respuestas pueden cachearse para optimizar performance.
  • Statelessness: el servidor no guarda estado entre requests.
  • Layered system: el cliente no sabe si habla con el servidor final o con un intermediario.
  • Interfaz uniforme, incluyendo HATEOAS (Hypermedia As The Engine Of Application State): la respuesta de un recurso incluye los links de las acciones posibles. Por ejemplo, un GET a una cuenta devuelve su número y balance junto con links a /deposit, /withdraw, /transfer y /close: la aplicación cliente descubre qué puede hacer con cada objeto a partir de la propia representación. Es un concepto poderoso pero no es estándar extendido en la industria.

REST en la práctica: herramientas y GitLab

Para explorar y probar APIs REST: curl (como un netcat para protocolos como HTTP: -X el verbo, -H los headers, -d el body; clave para scriptear pruebas sin interfaz gráfica), httpbin.org (servicios de ejemplo online) y Swagger (con ports como Flasgger para Flask/Python) que genera una UI de documentación y prueba dinámica de la API; una API sería suele desplegarlo en un /apidocs.

La API v4 de GitLab es un buen modelo mixto: entidades (/projects, /groups, /users, /snippets, /runners) más acciones necesarias que no son entidades (/search, /lint). 
# obtener proyectos (la coleccion completa, en plural)
curl -H Accept:application/json -X GET https://gitlab.com/api/v4/projects

# referencia anidada: usuarios de un proyecto
curl -X GET https://gitlab.com/api/v4/projects/3472737/users

# detalle de un usuario por id
curl -X GET https://gitlab.com/api/v4/users/43416

# crear un tag
curl -H Content-Type:application/json -X POST /projects/3472737/repository/tags \
     --data '{"tag_name":"stable", "ref":"master"}'

# borrar un branch (responde 204 No Content)
curl -X DELETE .../projects/3472737/repository/branches/issue-123
Sin id se obtiene la colección completa; con id, un único elemento. Las referencias anidadas suelen devolver una versión resumida de cada entidad (id, username, avatar) para acortar el chattiness: si devolvieran solo ids, el cliente tendría que pedir el detalle de cada uno. El costo es la consistencia: esa copia resumida puede quedar vieja si la información cambia rápido.

Identidad y relaciones

Identificar unívocamente una entidad entre sistemas es prioritario, y identidad no es nombre: el nombre puede cambiar (bautizo de nuevo a mi perro), la identidad no. Buscar /pet?name=Lassie puede traer todos los Lassie que haya; /pet/12345 es el lugar en toda Internet para ese perro. La URL define la identidad de la entidad, y el identificador debería llevar información de qué referencia:

// Bad ID                          // Better ID
{ "id": "12345",                   { "id": "/pet/12345",
  "type": "/dog",                    "type": "/dog",
  "name": "Lassie" }                 "name": "Lassie" }

Lo mismo para las relaciones: siempre usar URIs para referenciar otras entidades ("owner": "/users/98765" en lugar de "owner": "98765"), relativas si la entidad es del mismo sistema. Así las referencias se pueden navegar sin hardcodear en el cliente que "owner es un user".

Versionado de APIs y de objetos

Semantic Versioning (semver). Estándar de versionado Major.Minor.Patch (ej: 1.7.1) enfocado en comunicar retrocompatibilidad de la interfaz: Major se incrementa con cambios incompatibles con la versión anterior; Minor al agregar funcionalidad manteniendo retrocompatibilidad; Patch (o build) con correcciones que no afectan la interfaz.

¿Por qué importa tanto? Porque al desplegar una versión nueva no todos los consumidores se actualizan al mismo tiempo: el browser sí, pero las apps mobile que la gente no descarga y los servidores de terceros (que requieren coordinar con otra compañía) no. Por eso se mantienen versiones viejas de la API convivendo con la nueva, hasta fijar una fecha de deprecación.

Formas de versionar una API REST:

  • Versionado explícito en URL (/api/v4/...): fácil de usar y testear, RESTful compliant (interfaz uniforme). Es el estándar de facto.
  • HTTP custom header (ej: -H "Version: 1"): semánticamente incorrecto.
  • HTTP Accept header: semánticamente correcto (indica cómo quiero obtener el recurso, reutilizando el estándar), pero difícil de testear.

Versionado de objetos ≠ versionado de API. Dos tipos:

  • Format versioning: distintas representaciones de la misma entidad (invocar distintas versiones de la API, o filtrar campos del resultado, como el user completo vs resumido de GitLab). Es un versionado "cosmético".
  • Historical versioning: la misma entidad tiene distintas fotos a lo largo de su ciclo de vida. Ejemplo, páginas de una wiki: GET /api/pages/{id}, /latest, /{rev} o ?version={rev}.

Resumen de REST: es el estándar de facto de la industria; basado en entidades y cambios de estado, es ideal para manejar recursos pero complejo para ejecución remota de lógica de negocio (ahí asoman gRPC y las interfaces orientadas a procesos). La teoría importa, pero también el pragmatismo: el equilibrio entre pureza REST y practicidad es lo que diferencia a quien despliega a producción de quien solo discute diseño. Eso sí, sin pifiar en lo básico: usar HTTP/JSON directamente, identificar entidades unívocamente con URLs (no con nombres) y manejar bien versionado y queries.
