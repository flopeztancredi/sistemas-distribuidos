U02. Multitasking, multithreading y comunicaciones

Antes de distribuir un sistema entre computadoras hay que dominar la concurrencia dentro de una sola: threads, procesos, sus mecanismos de sincronización y los IPCs que provee el sistema operativo. Esta unidad recorre los tres modelos de multiprogramación, las propiedades que debe garantizar todo programa concurrente, los problemas clásicos que los ejercitan, y cierra con la base de comunicaciones (TCP/IP, sockets, mensajes sincrónicos y asincrónicos) sobre la que se construye todo lo que sigue en la materia.

Modelos de multiprogramación

Hay tres formas de tener varias unidades de ejecución trabajando a la vez, y se distinguen por qué recursos comparten:

MultithreadingMultiprocessingMulticomputing
Recursos compartidos Heap, data segment, file descriptors, code segment (read only) Code segment (read only), file descriptors abiertos pre fork Ninguno
Sincronización Soporte del SO (pthread mutex) o del runtime (threads de Java, .NET), IPCs IPCs: signals, shared memory, sockets, pipes/fifos, semáforos, queues, locks Mensajes ad hoc entre computadoras: cada sistema implementa sus propios mecanismos
Características Compartir información es sencillo, pero alto acoplamiento; un thread defectuoso afecta todo el proceso; escalabilidad muy limitada Compartir no es trivial; componentes separados y simples; más escalable y estable que threads; sin tolerancia a fallos de hardware o SO Comunicación compleja y central al diseño (ancho de banda, latencia, pérdida de mensajes); alta escalabilidad y tolerancia a fallos
La progresión es un trade off entre facilidad para compartir y robustez/escala. Cuanto más se comparte, más fácil es comunicarse y más frágil y acoplado queda el sistema. Multicomputing está en el extremo: no comparte nada, paga el costo de la red, y a cambio gana escalabilidad y tolerancia a fallos. Toda la materia es, en el fondo, aprender a vivir en esa columna.
Preguntado en finales: "¿Qué diferencia una arquitectura Multithreading de una Multiprocessing? Indique ventajas" (2022-08). Conviene responder con los recursos compartidos de cada una, y las ventajas cruzadas: threads comparten datos fácil pero se afectan entre sí; procesos aislan fallos y escalan mejor pero necesitan IPCs para comunicarse.

Propiedades de programas concurrentes

Safety property. Propiedad que debe ser siempre verdadera durante toda la ejecución (un invariante). Las dos clásicas: exclusión mutua (nunca hay dos procesos a la vez en la sección crítica) y ausencia de deadlocks.
Liveness property. Propiedad que debe ser eventualmente verdadera: algo bueno termina ocurriendo. Las clásicas: ausencia de starvation (todo proceso que quiere avanzar, en algún momento avanza) y fairness (el acceso a los recursos se reparte con justicia).
Safety dice "nunca pasa nada malo"; liveness dice "tarde o temprano pasa lo bueno". Un programa que no hace nada cumple todas las safety properties y ninguna liveness: por eso hacen falta las dos familias.

Asegurar las propiedades de safety es el pilar de la teoría de concurrencia, y hay dos caminos para lograrlo:

  • Basado en algoritmos: sin abstracciones especiales, solo condiciones lógicas sobre variables comunes que garantizan la sección crítica.
  • Basado en abstracciones: primitivas provistas por el SO o el lenguaje (semáforos, monitores, operaciones atómicas), combinables para construir mecanismos más complejos.

Exclusión mutua basada en algoritmos

  • Busy waiting: el proceso consulta una condición en un loop sin ceder el CPU. Es responsable de la mayoría de los problemas de performance en sistemas concurrentes.
  • Spin lock: el caso más simple de busy wait: while (flag): pass.
  • Algoritmos de espera: Dekker, Lamport (algoritmo del panadero), Peterson. Logran exclusión mutua entre procesos solo con variables compartidas y lógica.

El algoritmo de Peterson para dos procesos: cada uno levanta su bandera de intención y le cede el turno al otro; solo entra a la sección crítica si el otro no quiere entrar o si el turno es propio.

# Estado compartido
flag = [False, False]
turn = 0

# Proceso 0                          # Proceso 1
flag[0] = True                       flag[1] = True
turn = 1                             turn = 0
while flag[1] and turn == 1:         while flag[0] and turn == 0:
    pass                                 pass
# ... seccion critica ...            # ... seccion critica ...
flag[0] = False                      flag[1] = False

Operaciones atómicas y CAS

Operación atómica. Mecanismo provisto por el lenguaje o el hardware para actualizar variables u objetos sin usar mecanismos de sincronización explícitos: por ejemplo, contadores atómicos de tipos POD (int, char, double).
CAS (Compare and Swap). La operación atómica por excelencia para actualizar contenedores de forma segura en ambientes multithreading: compara el valor actual con el esperado y, solo si coinciden, escribe el valor nuevo. Todo en un único paso indivisible.
def cas(p, old, new):     # atomico, provisto por hardware
    if *p != old:
        return False
    *p = new
    return True

Ejemplo real: en Go, atomic.CompareAndSwapUint32(addr, old, new) devuelve si el swap se realizó. El patrón de uso es un loop: leer el valor, calcular el nuevo, intentar el CAS y reintentar si otro thread ganó la carrera.

Mecanismos de sincronización

Semáforos y mutex

Semáforo. Variable entera usada para controlar el acceso a recursos compartidos, definida por el conjunto de valores que puede adoptar (por ejemplo S = {0,1,2}). Operaciones válidas: wait decrementa S (y bloquea si S es 0), signal incrementa S.
Pensarlo como un dispensador de tokens: hay S turnos disponibles; cada proceso que quiere el recurso toma un token (wait) y lo devuelve al salir (signal). Si no quedan tokens, se espera bloqueado, sin busy waiting.
Mutex. Semáforo binario (S = {0,1}) usado para proteger secciones críticas: a lo sumo un proceso adentro a la vez.
La nomenclatura histórica P y V (de Dijkstra) confunde: clásicamente P es la operación que decrementa (wait, de "proberen") y V la que incrementa (signal, de "verhogen"). Lo importante para el examen es la semántica: wait decrementa y puede bloquear, signal incrementa y puede despertar a un proceso en espera.

Monitores

Monitor. Abstracción que encapsula en una única entidad las variables compartidas, las operaciones que las manipulan y el mecanismo de sincronización, con una cola de pedidos: solo un proceso ejecuta operaciones del monitor a la vez.

La ventaja sobre el semáforo suelto es que la exclusión mutua queda garantizada por construcción: el usuario del monitor no puede olvidarse de tomar el lock, porque el lock es implícito en cada operación.

En términos de flujo: los pedidos a un monitor se encolan y se sirven de a uno; cada llamada pasa primero por el mecanismo de sincronización interno antes de tocar las variables compartidas, así que nunca hay dos ejecuciones simultáneas dentro del monitor.

monitor class Account:
    balance = 0
    def withdraw(amount):          # cada metodo se ejecuta
        if balance < amount:       # con exclusion mutua
            return False           # garantizada por el monitor
        balance = balance - amount
        return True
    def deposit(amount):
        balance = balance + amount

Condition variables

Las condition variables son el ejemplo práctico de monitor: permiten que un proceso espere (sin busy waiting) hasta que se cumpla una condición sobre el estado compartido. El mutex asociado debe adquirirse antes de operar. Operaciones: wait bloquea al proceso hasta que otro lo despierte; notify despierta a un proceso en espera y notify_all a todos.

# Consumidor                       # Productor
cv.acquire()                       cv.acquire()
while not hay_item_disponible():   generar_item()
    cv.wait()                      cv.notify()   # o notify_all()
tomar_item()                       cv.release()
cv.release()
El wait va siempre dentro de un while que rechequea la condición, nunca un if: entre el notify y el despertar, otro proceso pudo haberse llevado el item (despertares espurios y carreras al despertar).

Barrera

Barrera. Punto de encuentro para N procesos o threads: cada uno que llega queda bloqueado hasta que llegaron todos; recién entonces la barrera "abre" y todos continúan a la vez.

Es el mecanismo natural para cómputos por rondas: N workers ejecutan cada uno su tarea de la ronda, esperan en la barrera a que sus pares terminen, y cuando todos llegaron arranca la ronda siguiente. Este ejercicio (N threads, M rondas de tareas) es el ejemplo canónico de la cátedra, y también se pide resolverlo con la abstracción BlockingQueue o con IPCs (shared memory con semáforos, o message queues).

Rendezvous

Rendezvous. Sincronización de a pares mediante pasaje de mensajes: dos procesos se encuentran en un punto de la ejecución; el que llega primero espera al otro, e intercambian el mensaje recién cuando ambos están presentes.
La barrera sincroniza a N procesos con un contador central; el rendezvous sincroniza de a dos con un mensaje. Cuando no hay memoria compartida (multicomputing), el rendezvous vía mensajes es el único tipo de sincronización posible, por eso es el puente conceptual entre esta unidad y el resto de la materia.

IPCs: comunicación entre procesos

IPC (Inter Process Communication). Mecanismos provistos por el sistema operativo que permiten la comunicación entre dos o más procesos, que ya no comparten memoria.

Propiedades comunes a todos los IPCs:

  • Su creación y destrucción exceden la vida del proceso: el usuario es responsable de su ciclo de vida. Un patrón habitual es tener un proceso launcher que los crea y un terminator que los libera.
  • Usualmente se identifican por nombre.
  • En Linux, todos los IPCs se ven como distintos tipos de archivos.

Cada mecanismo de sincronización entre threads tiene un análogo (o no) como IPC entre procesos:

Mecanismo entre threadsIPC equivalente entre procesos
Semáforo / mutexSemáforo (System V / POSIX)
Heap compartido (implícito entre threads)Shared memory (hay que pedirla explícitamente)
Monitor / lockFile lock
BarreraSin primitiva directa: se construye con semáforos o queues
Rendezvous / pasaje de mensajesSignals, message queues, pipes/fifos, sockets
Un ejemplo real de IPC a nivel kernel es el protocolo Binder de Android: cada proceso arma una transacción (BC_TRANSACTION) que el kernel entrega al proceso destino como BR_TRANSACTION, todo a través de una única llamada ioctl(), sin pasar por los mecanismos clásicos de System V (semáforos, shared memory o message queues).

Signals

  • Existen 31 tipos distintos (kill -l). Cada proceso decide cuáles handlear, salvo SIGSTOP y SIGKILL, que no pueden capturarse ni ignorarse.
  • Signals estándar: SIGINT y SIGTERM para graceful quit, SIGSEGV por problemas de memoria, SIGABRT por assertions del código.
  • En procesos multithreaded, la propagación de signals se controla con máscaras por thread (mask setting).
docker stop envía SIGTERM al proceso principal del contenedor: el proceso puede handlearla para cerrar ordenadamente (liberar IPCs, cerrar sockets, terminar hijos). Si en cambio recibe SIGKILL (señal 9, la que docker manda tras el timeout), termina sí o sí, sin posibilidad de handler. De ahí que el graceful shutdown de los TPs se implemente handleando SIGTERM. Otro caso real: libcURL usa SIGALRM para implementar sus timeouts de resolución DNS.

Shared memory

  • Mecanismo del SO para compartir un bloque de memoria entre procesos: la abstracción que entre threads no hace falta, porque el heap ya es compartido.
  • Su tamanio se define al crearla.
  • Requiere sincronización externa (típicamente un semáforo/mutex) solo cuando dos procesos no pueden acceder a la vez, por ejemplo un contador compartido; una cache de slots independientes con un único escritor por slot puede no necesitarla.

File locks

Control de acceso sobre un file descriptor: flock(fd, operation). Dos tipos:

  • Shared lock (R): lock de solo lectura; múltiples read locks simultáneos permitidos.
  • Exclusive lock (W): lock de lectura y escritura; solo uno a la vez por archivo, y excluye también a los shared.

La regla de bloqueo: mientras haya al menos un shared lock activo, un exclusive lock pedido debe esperar a que todos se liberen; y mientras el exclusive lock esté activo, cualquier lock nuevo (shared o exclusive) espera a que se libere.

Pipes y FIFOs

  • Pasaje de información directa entre 2 procesos, con la API de archivo de Linux para leer y escribir.
  • Unnamed pipes (pipes): comunican padre e hijo; dejan de existir al terminar el proceso.
  • Named pipes (FIFOs): comunican dos procesos cualesquiera; viven en el SO, exceden la vida del proceso.

El buffer de un pipe es acotado (en Linux moderno, 64 KiB por defecto): escribir sobre un pipe lleno bloquea al escritor, leer de uno vacío bloquea al lector. Esa semántica de bloqueo es la que lo vuelve también un mecanismo de sincronización.

Message queues (System V)

  • Los procesos escriben y reciben bloques de bytes; los mensajes leídos se remueven de la cola. El tamanio del buffer se define en la creación.
  • Cada mensaje lleva un campo mtype: el sender debe enviar con mtype > 0; el receptor que pide mtype = 0 recibe cualquier mensaje sin importar el tipo; el caso esotérico mtype < 0 recibe el mensaje de menor tipo entre los que no superan el valor absoluto pedido.

Sockets

Comunican dos procesos a través de un canal con dos endpoints: socket(domain, type, protocol). Es el único IPC que además funciona entre máquinas, por eso es la puerta al multicomputing.

  • Domain: AF_UNIX (Unix socket, local), AF_INET / AF_INET6 (socket de red).
  • Type: SOCK_STREAM (TCP), SOCK_DGRAM (UDP), SOCK_RAW (acceso crudo a la capa inferior, sin protocolo de transporte).

Problemas clásicos de concurrencia

Productor consumidor

Productores agregan paquetes a un buffer y consumidores los extraen. El acceso al buffer debe sincronizarse, y hay dos situaciones de bloqueo: el productor que intenta agregar con el buffer lleno y el consumidor que intenta extraer con el buffer vacío. Una decisión clave del enunciado es si el buffer es acotado o infinito: con buffer infinito solo bloquea el consumidor.

Este problema es el núcleo de casi todo sistema distribuido real: una work queue de RabbitMQ es exactamente un productor consumidor donde el buffer es el broker. Resolverlo con semáforos (uno contando lugares libres, otro contando items, más un mutex) es el ejercicio base.

Lectores escritores

Dos tipos de procesos acceden a una memoria compartida: lectores (pueden coexistir) y escritores (necesitan exclusividad). Las variantes del problema se definen en función de fairness y starvation:

  • Prioridad lectores: los escritores esperan a que los lectores liberen el recurso (riesgo de starvation de escritores).
  • Prioridad escritores: los lectores esperan a que los escritores liberen el recurso (riesgo de starvation de lectores).
  • Acceso por tiempo limitado: ambos tipos acceden con turnos acotados, buscando fairness.

Notar el paralelismo con los file locks: shared lock es el lector, exclusive lock es el escritor.

Otros problemas clásicos que la cátedra menciona para practicar: el barbero dormilón, los filósofos comensales y los fumadores de cigarrillos.

El paquete IP (capa Internet) lleva en su header las direcciones de origen y destino, TTL, protocolo, checksum y campos de fragmentación. Sobre IP viven los dos protocolos de transporte que importan para la materia.

El header IP básico ocupa filas de 32 bits: versión e IHL comparten fila con Type of Service y Total Length; le siguen Identification con Flags y Frag Offset; luego TTL, Protocol y Header Checksum; y por último las direcciones de origen y destino, con Options opcional antes de los datos.

TCP es orientado a streams, no a mensajes: garantiza que los bytes llegan completos y en orden, pero no respeta los límites de los send(). Un recv() puede devolver medio mensaje o dos mensajes juntos (short reads): delimitar donde empieza y termina cada mensaje (framing) es responsabilidad del programador. Este detalle se pregunta seguido cuando piden comparar TCP con abstracciones de mensajes discretos como los MOMs.
Preguntado en finales, de forma recurrente: "Suponga que debe implementar un protocolo de health-check de server a clientes mediante sockets. ¿Qué condiciones se deberian cumplir para que sea más conveniente utilizar UDP frente a TCP?" (2024-07, 2024-12). La respuesta esperada: si los mensajes son periódicos y toleran pérdida (basta que llegue alguno para dar por vivo al proceso), UDP conviene porque no paga conexión ni retransmisiones; TCP es contraproducente porque retransmite heartbeats viejos antes de entregar el nuevo, agregando latencia y hasta falsos negativos bajo congestion. Además UDP es más liviano si hay que chequear muchos procesos.
También preguntado: "Indique ventajas y desventajas de utilizar comunicación por sockets TCP frente al pasaje de mensajes por colas mediante MOM" (2025-02, 2025-07). Desde esta unidad aporta: TCP da entrega y orden solo mientras la conexión vive, es stream (framing manual) y es liviano y de baja latencia; las garantías ante desconexión y los mensajes discretos los agrega el MOM (ver unidad 5).

Programación con sockets

Primitivas: socket(), bind(), listen(), accept(), connect(), send(), recv(), close().

  • Flujo TCP: el server hace socket, bind, listen, accept; el cliente hace socket, connect. El accept devuelve un nuevo file descriptor por cada conexión aceptada; el socket original sigue escuchando.
  • Backlog de listen: limita las conexiones pendientes de aceptar, no las ya establecidas.
  • Flujo UDP: sin conexión: el server hace socket, bind y luego recvfrom/sendto; el cliente directamente sendto/recvfrom. No hay listen ni accept.

Mensajes sincrónicos vs asincrónicos

Mensaje sincrónico. El emisor envía el request y queda bloqueado (idle) hasta recibir la response: su línea de tiempo tiene un hueco de inactividad entre el envio y la respuesta.
Mensaje asincrónico. El emisor envía el request y continúa activo con otro trabajo; la response llega más tarde y se procesa cuando llega.
El diagrama mental: dos líneas de tiempo (cliente y servidor) con flechas request y response. En el caso sincrónico el tramo del cliente entre ambas flechas esta "apagado"; en el asincrónico esta "prendido". La elección define cuanto desacopla el sistema: los MOMs y los patrones de mensajeria de las unidades siguientes explotan la asincronia.
Relacionado en finales: "¿Cómo se garantiza que un algoritmo o protocolo sea sincrónico en el contexto de sistemas distribuidos?" (2025-07). La noción completa de sistema sincrónico (cotas conocidas de cómputo y comunicación) se desarrolla en la unidad de tiempo y sincronismo; desde aca conviene tener claro que sincrónico implica poder esperar la respuesta con un límite de tiempo conocido.

Congestion de red

La red tiene capacidad finita. A medida que crece la carga ofrecida, el throughput crece linealmente hasta acercarse a la capacidad; ahí los buffers de los routers se llenan, aparecen retransmisiones y, sin control, el throughput colapsa (congestion collapse): más tráfico ofrecido resulta en menos datos útiles entregados. El delay se comporta peor: crece de forma explosiva cuando la utilización se acerca al 100%.

  • Throttling: limitar deliberadamente la tasa de envio para operar antes del punto de colapso; es la base del control de congestion de TCP (sliding window).
  • Para el diseño de sistemas distribuidos la lección es directa: nunca planificar para operar la red al límite, porque cerca de la saturación la latencia se degrada mucho antes que el throughput.
  • Conviene distinguir el delay promedio de todos los paquetes ofrecidos, que diverge cerca de la saturación porque arrastra las retransmisiones, del delay promedio de los paquetes que efectivamente se entregan, que se satura pero no diverge.
