U05. Mensajes, grupos, middlewares y MOMs; RabbitMQ

Esta unidad recorre la cadena completa de la comunicación en sistemas distribuidos: como se representan los mensajes en el cable (formato, framing, sincronismo), como se abstrae un conjunto de procesos en un grupo de comunicación, que es un middleware y que tipos existen, y por que los Message Oriented Middlewares (MOMs) son la pieza central de la materia. Cierra con RabbitMQ, el MOM centralizado que se usa en los trabajos prácticos, con sus colas, ACKs y exchanges. Es una de las unidades más preguntadas en finales.

Mensajes: formato, longitud y sincronismo

Antes de hablar de middlewares hay que resolver un problema más básico: dos procesos que se comunican tienen que acordar como se ve un mensaje. Eso implica tres decisiones: formato (binario o texto), delimitación (donde empieza y termina cada campo) y modo de interacción (sincrónico o asincrónico).

Formato binario vs texto plano

BinarioTexto plano
PerformanceAlta: mensajes chicos, la compresión puede no ser necesariaBaja: más bytes por el mismo dato, comprimir agrega overhead
SerializaciónAutogeneración de código (Protobuf, Thrift, ASN.1); no todos los lenguajes tienen soporteFormatos human readable (JSON, XML) o serialización básica (HTTP, SMTP)
InteracciónRequiere un cliente específico y un decoder para interpretar los mensajesAlcanza un cliente genérico si se conoce el protocolo (curl contra una API REST); fácil de debuggear
Con Protobuf se define el mensaje una sola vez en un .proto (message Person { required string name = 1; required int32 id = 2; optional string email = 3; }) y el compilador protoc genera el código de serialización para cada lenguaje: un proceso en Java puede escribir la Person y otro en C++ deserializarla, sin escribir parsers a mano. Del lado texto plano, el ejemplo típico es un POST HTTP con body JSON hecho con curl: cualquier humano lo lee y lo reproduce.
Preguntado en finales: "Explique la necesidad del uso de protocolos binarios y no-binarios para la comunicación en un sistema distribuido. De un ejemplo de protocolos conocidos en estas dos categorías" (2023-07, 2025-07). Se espera: binarios minimizan tamaño y maximizan performance pero son poco interpretables (ej: Protobuf); texto plano es más pesado pero fácil de leer y debuggear (ej: HTTP/JSON). Ojo con las correcciones típicas: acomodar campos en JSON "sin serializar" no existe (armar el JSON ya es serializar) y un protocolo con longitud fija para unos campos y variable para otros es un esquema mixto.

Longitud de paquete (framing)

TCP entrega un stream de bytes, no mensajes: delimitar donde termina cada campo es responsabilidad del protocolo de aplicación. Hay tres esquemas:

  • Bloques fijos: cada dato tiene longitud fija. Fácil de serializar, pero suboptimo con tipos de longitud variable como strings.
  • Bloques dinámicos: se usa un separador que delimita el campo, o un prefijo de longitud. Agrega un pequeño overhead de bytes extra.
  • Esquema mixto: los parámetros fijos (integers) van sin delimitador; los variables llevan longitud o separador. Es lo más comun en la práctica.
TLV (Type - Length - Value). Cada parámetro se codifica como un tipo de tamaño fijo, una longitud de tamaño fijo y el valor variable, que además admite subtipos anidados. Con un mini protocolo donde 01 es integer, 02 es string y 03 es un compuesto Dirección, la dirección "Alsina 2B" se serializa como 03 11 (dirección, 17 bytes) que contiene 01 06 41 6c 73 69 6e 61 (calle "Alsina"), 02 04 00 00 00 02 (número 2) y 03 01 42 (unidad "B").
TFTP: framing mixto y un caso borde clásico

TFTP delimita con esquema mixto: el paquete Read/Write lleva opcode fijo de 2 bytes y filename como string terminado en byte 0; el paquete Data lleva opcode, número de bloque y hasta 512 bytes de datos; el ACK lleva opcode y número de bloque. El receptor sabe que la transferencia término cuando recibe un bloque de menos de 512 bytes. El caso borde: si el archivo mide un múltiplo exacto de 512 (por ejemplo 512 bytes), el emisor debe mandar un último bloque de 0 bytes de datos, porque si no el receptor se quedaria esperando. Un archivo de 513 bytes viaja como un bloque de 512 y uno de 1.

Sincronización de señales

En ciertos protocolos (sobre todo de bajo nivel) hace falta saber donde empieza una señal para interpretar la secuencia de bits. El sensor de humedad y temperatura DHT11 es el ejemplo de cátedra: transmite por un único pin, arranca con una señal de sincronismo y después envía 40 bits (parte entera y decimal de humedad, parte entera y decimal de temperatura, y un byte de checksum). Sin la señal inicial el receptor no puede alinear los bits.

Mensajes sincrónicos vs asincrónicos

En el modo sincrónico el cliente envía el request y queda bloqueado (idle) hasta recibir la respuesta. En el modo asincrónico el cliente sigue procesando después de enviar y la respuesta llega más tarde, como un evento separado. Esta distinción a nivel mensaje reaparece amplificada a nivel middleware en los modelos sincrónico y asincrónico del MOM.

Grupos de comunicación

Grupo de comunicación. Abstracción que permite ver a una colección de procesos como una única entidad: un mensaje enviado al grupo llega a todas o algunas de las entidades que lo componen. Los grupos son dinámicos: deben poder crearse y destruirse en todo momento, y los procesos deben poder suscribirse y desuscribirse, para lo cual el sistema debe ofrecer primitivas (join, leave).
La gracia del grupo es que el emisor es agnostico de la composición del sistema: no sabe cuantos miembros hay ni donde están. Si mañana hacen falta más workers o más réplicas, se levantan procesos nuevos que se unen al grupo y nadie más cambia su comportamiento. Por eso los grupos son la base de la escalabilidad, la elasticidad y la replicación para tolerancia a fallos.
Preguntado en finales: "¿Qué es un grupo de comunicación? ¿Qué utilidad presenta este concepto a la hora de diseñar un sistema escalable?" (2023-07, 2025-07). La respuesta fuerte combina la definición (abstracción, entrada y salida transparente de miembros) con la utilidad: escalar agregando miembros sin que el emisor lo note, replicar para tolerancia a fallos y facilitar service discovery y coordinación.

Topologías

  • Anillo: cada nodo se conecta solo con el anterior y el siguiente (pocas conexiones), pero un mensaje puede tener que recorrer toda la red para llegar a destino si el flujo no es bidireccional.
  • Punto a punto (clique): comunicación directa y rápida, pero la cantidad de conexiones explota al crecer la cantidad de nodos.
  • Grupos jerárquicos: útiles cuando un nodo debe cascadear mensajes hacia nodos hijos.

Sobre una misma topología, la difusión puede ser centralizada (un solo nodo, la raiz, envía el mensaje a todos los que corresponde) o descentralizada (un nodo envía el mensaje inicial y los demas lo propagan). La topología a elegir depende del caso de uso, pero la condición irrenunciable es que el grafo sea conexo: siempre debe existir un camino entre cualquier par de nodos.

Atomicidad de mensajes

Atomicidad de mensajes. Propiedad por la cual un mensaje enviado a un grupo se entrega (deliver) a todos los destinatarios o a ninguno.

Para garantizarla hace falta: ACK de los mensajes, demorar el delivery de los paquetes recibidos (retenerlos en una hold-back queue hasta confirmar que todos pueden entregarlos), y reintentos frente a caída de receptores, caída del coordinador, no recepción de mensajes y no recepción de ACKs. La cátedra menciona que en la práctica se apoyan en protocolos de commit como 2PC o 3PC; 2PC asume que la operación de commit no falla, por lo que se busca minimizar el trabajo hecho en esa fase.

No confundir recepción con entrega (deliver): un proceso puede haber recibido el mensaje por la red pero retenerlo sin entregarlo a la aplicación. La atomicidad se define sobre el deliver. Un mensaje se considera estable recien cuando hay confirmación de que todos los miembros lo tienen; solo entonces se entrega.
Preguntado en finales: "¿Qué se entiende por 'Atomicidad de Mensajes' en el contexto de grupos de comunicación? ¿Con que estrategias es posible garantizarla?" (2024-07, 2024-12). Estrategias esperadas: ACKs, hold-back queues con delivery demorado hasta estabilidad del mensaje, y reintentos ante caídas; estas garantías las suele proveer un MOM.

Middlewares

Middleware. Software de conectividad que ofrece un conjunto de servicios que hacen posible el funcionamiento de aplicaciones distribuidas sobre plataformas heterogéneas. Es una capa de software situada entre el sistema operativo y las aplicaciones, que provee una vista única del sistema.
De las varias definiciones que recopila la cátedra, todas apuntan a lo mismo: hay una capa en el medio que abstrae a la aplicación de los pormenores de la comunicación. La app 1 quiere hablar con la app X y no le importa donde esta, como se llega ni que pasa en la red. Toda la complejidad de la distribución queda en el middleware, no en la lógica de negocio.

Objetivos de un middleware

  • Transparencia: se oculta la distribución y el sistema responde como si fuera una única computadora, respecto de acceso, ubicación, migración, replicación, concurrencia, fallos y persistencia. Ejemplo: si un recurso que se obtenia atravesando una cadena de nodos pasa a servirse desde una cache, la aplicación no cambia; el cambio queda contenido en el middleware.
  • Tolerancia a fallos: sistemas confiables que se comportan de manera predecible incluso frente a fallos, abarcando availability, reliability, durability, safety y maintainability. La idea no es que el sistema no falle nunca, sino que ante una falla se degrade (por ejemplo responda más lento) pero siga dando servicio hasta repararse.
  • Acceso a recursos compartidos: eficiente, transparente y controlado.
  • Sistemas distribuidos abiertos: estandares claros de sintaxis y semántica de los servicios ofrecidos (interfaces), para lograr interoperabilidad y portabilidad. Si el middleware se reestructura internamente (se cambia una tecnología por otra, como reemplazar Docker por otro container engine), la interfaz se respeta y el nivel de usuario no se entera.
  • Comunicación de grupos: el middleware provee las primitivas para crear grupos y comunicarse dentro de ellos (broadcasting, multicasting), y facilita la localización de elementos y la coordinación de tareas.

Vista física: centralizado vs distribuido

En la implementación centralizada, el middleware vive en uno o más hosts dedicados (Middleware Host) que concentran los servicios de discovery, orquestación, seguridad y persistencia; los clientes se comunican con el a traves de una client library (una SDK o API que expone el contrato del middleware). Del otro lado del host central hay Nodes de backend que corren su propio Middleware Agent: son los recursos (cómputo, almacenamiento) que el host orquesta y expone mediante esos servicios. El cliente nunca habla directamente con un Node: toda la comunicación pasa por el Middleware Host, que queda en el medio de los dos tipos de participante. En la implementación distribuida no hay host central: cada servidor lleva embebido un agente del middleware (Middleware Agent) y los servicios están repartidos entre todos, mientras que los clientes siguen usando su client library sin agente propio. Cualquier cliente puede conectarse a cualquiera de los servidores (no hay una asignación fija cliente-servidor), y los servidores a su vez se comunican directamente entre si para mantener consistentes los servicios repartidos. Es más flexible y escala con facilidad (se inyectan nodos nuevos sin tocar el resto) pero es más difícil de mantener; en la práctica es comun terminar con hosts dedicados.

Clasificación de middlewares

  • Transactional Processing: garantizan transaccionalidad de operaciones sobre datos, conectan muchas fuentes de datos con acceso transparente al grupo, y tienen políticas de reintentos y retención de datos frente a caídas internas. Es una categoría de los 90, nacida del auge de las bases de datos (transacciones distribuidas en vez de conexión punto a punto con la base); no perduro.
  • Object Oriented: los mensajes van hacia objetos distribuidos que viven dentro del middleware; cada cliente tiene una referencia al objeto compartido y el middleware propaga las modificaciones, usando un esquema de marshalling para transmitir la información. Nacio con el auge de la orientación a objetos; el ejemplo clásico es CORBA, un estandar tan complejo que fracaso.
  • Procedure Oriented: el middleware trabaja como un servidor de funciones invocables desde cualquier nodo; los servicios se pueden explorar y ejecutar pero no guardan estado entre invocaciones. Es la idea detras de RPC, y su descendencia sigue viva: las arquitecturas serverless (Lambda de AWS) son funciones que se ejecutan reactivamente ante un request o un mensaje en una cola.
  • Message Oriented (MOM): funciona como un sistema de mensajeria entre las aplicaciones que lo usan. Los mensajes pueden publicarse bajo un tópico para que los interesados los reciban (modo Information Bus) o enviarse a un destinatario definido (modo Queue). Es el tipo en el que se centra la materia.
  • Reflective: middlewares de configuración dinámica.
Preguntado en finales, en la parte práctica: diseñar un middleware de comunicación de grupos. Formas típicas: "Describa como implementaria un middleware que garantice la comunicación de grupo con tres grupos x, y, z, miembros que se unen en cualquier momento, y envio solo a todos los miembros del grupo" (2024-07, también listado en Notion como pregunta recurrente) y "Defina los lineamientos de implementación para un middleware que resuelva el chat de un videojuego multiplayer con equipos, indicando firmas y como se invocarian" (2025-03). Se resuelven con pub/sub por tópico (un canal por grupo), un servicio de membresia con primitivas join/leave, y multicast confiable con ACKs y hold-back queues para respetar la atomicidad.

MOM: Message Oriented Middleware

MOM. Middleware que implementa la comunicación de grupo de forma transparente a las aplicaciones, basando todo su funcionamiento en un concepto simple: comunicar mensajes entre aplicaciones. Resuelve problemas de transparencia respecto de ubicación, fallos, performance y escalabilidad.

Un MOM puede ser centralizado (las aplicaciones se comunican a traves de un message broker, como RabbitMQ) o distribuido (las aplicaciones se comunican entre si con la lógica de mensajeria embebida en cada una, como ZeroMQ, que se ve en la unidad de patrones de comunicación).

Modelo sincrónico vs asincrónico del MOM

Sincrónico: se modela como una conexión punto a punto y permite obtener respuestas instantaneas a pedidos concretos, pero no permite implementar transparencia frente a errores: si el receptor no esta, el emisor lo sufre.

Asincrónico: se modela naturalmente con colas, y la arquitectura soporta periodos de discontinuidad del transporte. Esta es la propiedad clave: el sistema funciona con ambos extremos activos, con solo el sender activo (los mensajes quedan encolados), con solo el receiver activo (drena lo pendiente) o incluso con ninguno activo (los mensajes persisten en el MOM). El contra: es complejo recibir respuesta a los pedidos realizados; como mínimo hacen falta colas adicionales para el retorno de la información.

Preguntado en finales: "Indique las ventajas y desventajas de utilizar comunicación por sockets TCP frente al pasaje de mensajes por colas mediante MOM en un sistema distribuido típico" (2025-02, 2025-07). Puntos que suman: TCP es orientado a streams (el programador debe hacer el framing de los mensajes, ver longitud de paquete) y acopla temporal y espacialmente (ambos activos, conocerse IP:puerto); el MOM maneja mensajes discretos, desacopla en el tiempo, ofrece patrones (working queues, pub/sub, routing) y garantías de entrega, a costa de más infraestructura (broker), overhead y latencia por el almacenamiento intermedio. Criterio: TCP para request-reply sincrónico de baja latencia; MOM para integración de sistemas heterogéneos y tareas asincrónicas que no deben perderse.

Operaciones comunes

  • put: publicación de un mensaje.
  • get: bloquear hasta que haya un mensaje; luego eliminarlo de la cola y retornarlo.
  • poll: revisar mensajes pendientes sin bloquear.
  • notify: asociar un callback que el MOM ejecuta frente a la publicación de ciertos mensajes.

Colas de mensajes y brokers

Dentro del MOM pueden existir varias colas, con nombre y longitud definidos. Los clientes suelen contar con colas privadas intermedias, y el MOM le garantiza al emisor que el mensaje será insertado. Cuando el MOM es centralizado, el componente central se conoce como broker:

  • Provee transparencia de localización tanto al emisor como al receptor.
  • Soporta lógica en el middleware para filtrar y modificar mensajes (filtering, routing).
  • Brinda un punto de control y monitoreo del sistema.

RabbitMQ: un MOM centralizado

RabbitMQ es el broker que usa la cátedra para los TPs. El cambio mental respecto de programar con sockets: aca no hay sockets, hay colas. El productor no sabe cuantos consumidores existen ni donde están, y viceversa; lo único que ambos conocen es la cola, que es el canal de comunicación que abstrae todo. Por eso el mismo sistema funciona igual con 1 productor y 1 consumidor que con 3 productores y 20 consumidores.

Colas, ACK y durabilidad

  • Tipos de cola: nombradas (productor y consumidor conocen el nombre), task queues (una cola de trabajo compartida por un pool de workers) y anónimas (el broker les genera el nombre; se usan con exchanges).
  • Declaración idempotente: queue_declare crea la cola si no existe y no hace nada si ya existe. Las propiedades deben coincidir: no se puede declarar la misma cola durable de un lado y no durable del otro, alguna de las llamadas falla.
  • Acknowledge: el ACK es la forma de decirle al broker "ya termine de procesar este mensaje, podes borrarlo". Es automático por defecto (auto_ack), pero con ACK manual el mensaje permanece en la cola (sin re-entregarse) hasta que el consumidor confirma. Si el consumidor muere antes de hacer ACK, el broker detecta la caída del channel y re-entrega el mensaje a otro consumidor: nada se pierde. La regla práctica: hacer ACK recien después de procesar el mensaje y despacharlo o persistirlo.
  • Durabilidad: para sobrevivir reinicios del broker hay que definirla en dos niveles: la cola debe declararse durable=True y cada mensaje debe publicarse con delivery mode persistente. Ambas propiedades deben cumplirse. Además, en un entorno Docker el directorio de datos de RabbitMQ necesita un volumen, si no la cola muere con el contenedor aunque sea durable.
  • Prefetch: por defecto RabbitMQ despacha a los consumidores en round robin, lo que hace que un worker lento frene mensajes que otro worker libre podría procesar (la cola crece mientras un consumidor está bloqueado). Con basic_qos(prefetch_count=1) el broker no le da un mensaje nuevo a un consumidor hasta que hizo ACK del anterior: el worker rápido agarra más trabajo y se obtiene un pool de workers con balance de carga real.
# Task queue con ACK manual y durabilidad (estilo pika)
channel.queue_declare(queue="task_queue", durable=True)
channel.basic_qos(prefetch_count=1)

def callback(ch, method, properties, body):
    procesar(body)                      # procesar ANTES de ackear
    ch.basic_ack(delivery_tag=method.delivery_tag)

channel.basic_consume(queue="task_queue", on_message_callback=callback)
channel.start_consuming()               # bloqueante: enciende la maquinaria
El ACK y la durabilidad protegen contra fallas distintas. El ACK manual cubre la caída del consumidor (el mensaje sacado pero no confirmado se re-entrega); la cola durable más el mensaje persistente cubren la caída del broker. Un sistema tolerante a fallos con RabbitMQ necesita las dos cosas, y aun así la re-entrega implica que un mensaje puede procesarse más de una vez (semántica at-least-once): conviene que los mensajes sean idempotentes.
Preguntado en finales: "Explique que estrategias puede implementar un MOM para garantizar tolerancia a fallos. Ejemplifique con algun MOM que conozca o haya implementado" (2022-08). Respuesta armada con esta sección: ACK manual con re-entrega ante caída del consumidor, colas durables y mensajes persistentes ante caída del broker, y garantía de inserción al emisor; RabbitMQ como ejemplo concreto.
Preguntado en finales: "Asumiendo un equipo de hasta 10 agentes de atención al cliente, defina como implementar un middleware distribuido que permita a los agentes llamar al siguiente número en fila. ¿Dónde almacenaria la información del último número llamado?" (2024-12). Es una task queue de manual: una única working queue de la que los agentes toman números de a uno, ACK al completar la llamada (si el agente cae sin ACK, el número se re-encola para otro), y el último número llamado se propaga a un proceso sink o base de datos compartida.

Tolerancia a fallos del broker

ACK y durabilidad cubren dos fallas: la caída del consumidor (el mensaje se re-entrega) y el reinicio del broker (el mensaje sobrevive en disco). Pero ninguna de las dos cubre el caso en que el broker queda caído: mientras no vuelva, no hay servicio de mensajería, y un MOM centralizado es por definición un punto único de falla. Para eso hace falta redundancia y no solo persistencia:

  • Clustering: varios nodos de broker forman un cluster y comparten la definición de exchanges, colas y usuarios. Sube la capacidad y permite que los clientes se conecten a cualquier nodo, pero por sí solo no réplica el contenido de las colas: si cae el nodo dueño de una cola, esa cola no está disponible.
  • Colas replicadas: el contenido de la cola se mantiene en varios nodos. En RabbitMQ, las quorum queues (basadas en Raft, hoy la opción recomendada) eligen un líder por cola y replican en los seguidores, tolerando la caída de la minoría; las mirrored queues son el mecanismo anterior, con espejado maestro-espejos. Cuando cae el nodo líder, otro toma su lugar y la cola sigue disponible.
  • Reconexión del cliente: nada de lo anterior sirve si la librería cliente no reintenta contra otro nodo. Hay que configurar la lista de nodos y la política de reconexión, y asumir que un reintento puede duplicar un envío (de nuevo, at-least-once e idempotencia).
Replicar cuesta: cada mensaje se escribe en varios nodos antes de confirmarse, así que sube la latencia de publicación y baja el throughput. Es el mismo trade-off que en replicación de datos, y por eso conviene replicar las colas críticas y no todas.
Preguntado en finales: cómo se garantiza que no se pierdan mensajes ante caídas al usar un MOM (2022-08). Una respuesta completa cubre los tres niveles: ACK manual para la caída del consumidor, cola durable más mensaje persistente para el reinicio del broker, y cluster con colas replicadas (quorum queues) para que la caída de un nodo no deje al sistema sin mensajería. Contestar solo durabilidad deja afuera el punto único de falla.

Exchanges

Exchange. Componente de RabbitMQ que recibe mensajes de los productores y los rutea hacia colas según una estrategia configurable. Tipos: fanout, direct, topic y headers.
Un exchange se puede pensar como un load balancer: uno le define a Rabbit "cuando llegue este mensaje, envialo a estas colas bajo este patrón". El productor deja de publicar a una cola concreta y publica al exchange; que colas reciben cada mensaje lo deciden los bindings.
Un exchange no es una cola: no almacena nada. Si llega un mensaje cuya routing key no matchea ningun binding (o no hay colas bindeadas), el mensaje se pierde silenciosamente. Si ciertos mensajes no deben perderse, el despliegue tiene que garantizar que siempre exista una cola bindeada que los reciba. Otro detalle que confunde: el parámetro routing_key de basic_publish es un comodin, cuando se publica con exchange vacio significa "nombre de cola destino", y cuando se publica a un exchange significa "clave de ruteo"; es un abuso de notación de la API.

Patrones con exchanges

  • Publisher-Subscriber (exchange fanout): el publisher envía mensajes a un exchange fanout, que hace broadcast de todo lo que recibe a todas las colas bindeadas. Cada subscriber crea una cola anónima (declara una cola con nombre vacio, el broker le devuelve el nombre generado) y la bindea al exchange. La cola es anónima porque nadie la referencia directamente: el productor solo conoce el exchange.
  • Routing (exchange direct): el productor adosa a cada mensaje una routing_key; el consumidor bindea su cola al exchange con las keys que desea recibir (puede bindear varias). El exchange redirige cada mensaje a las colas bindeadas con esa key exacta. Ejemplo de cátedra: un pipeline de logs donde los mensajes llevan key info, warning o error, un consumidor escucha solo error y otro todo menos debug; los mensajes debug, que nadie bindeo, se pierden.
  • Topic (exchange topic): igual que routing pero la routing key es un conjunto de palabras separadas por punto y los bindings admiten patrones: * sustituye exactamente una palabra y # sustituye una o más. *.orange.* matchea tres palabras con orange en el medio; lazy.# matchea todo lo que empiece con lazy. Permite cosas como particionar mensajes entre consumidores según un patrón sobre los primeros caracteres de un hash.
  • Headers: rutea por headers del mensaje en vez de routing key. La cátedra lo menciona pero no lo desarrolla.

Operación práctica

  • Interfaz de administración: RabbitMQ trae una UI web para ver conexiones, channels, exchanges y colas: el rate de mensajes, cuantos hay encolados, que cola crece o se bloquea. Permite publicar mensajes a mano, sacar mensajes (con o sin ACK), purgar colas y ver o modificar bindings. Es una herramienta central para debuggear el TP: la cantidad de mensajes sin ACK delata a un consumidor trabado.
  • Bootstrapping: el arranque de un sistema distribuido es un problema en si mismo: si productores y consumidores levantan antes que el broker, fallan al conectarse. Licencias validas: políticas de restart on failure o sleeps al inicio en los ejemplos, o directamente levantar primero RabbitMQ (por ejemplo docker compose start rabbitmq), esperar a que este operativo y después levantar el resto. Documentar la secuencia de arranque es práctica normal en la industria.
  • Retention policies: las colas durables permiten usar al broker como almacenamiento temporal con políticas de retención (descartar mensajes por antiguedad o por espacio), el esquema típico de un pipeline de logs con un broker que amortigua entre los procesadores y la base de indexación.
